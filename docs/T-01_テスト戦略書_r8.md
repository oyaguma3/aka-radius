# T-01 テスト戦略書 (r8)

## 1. 概要

aka-radius の試験の層、道具、合格の基準、CI と検証機の通しの分け方を決める。試験の一つひとつは Go のコード（`*_test.go`）と CI の設定（`.github/workflows/`）が正で、本書には一覧を写さない。

| 参照先 | 内容 |
|---|---|
| 設計概要（`docs/design-overview.md`）§15 | 試験の層（MVP の決定） |
| E-01 開発環境セットアップガイド | 手元の環境、Makefile、手元の compose |
| E-02 コーディング規約（簡易版） | インターフェースと偽物の作り方 |
| S-01 eapaka_test利用ノウハウ | eapaka_test の設定とケース、刻印を付ける経路 |
| aka-mvpset の `verify/stage2/` | 段階 2 の終わりの検証機の通し（道具と結果） |

本PoC（eapaka-radius-server-poc）の手順書の試験（T-02 単体テスト仕様書・T-03 結合テスト仕様書・T-04 E2Eテスト仕様書）は廃止した。単体と結合は Go のコードで CI が走らせ、E2E と規模の試験は aka-mvpset で行う。

### 2.1 単体

- 1 つのパッケージの中の振る舞いを確かめる。重いのは、EAP の状態機械（AT_IDENTITY からの IMSI、再同期は 1 回まで）、判定の順（有無 → 状態 → 刻印 → ルール）、刻印（信頼の印、2 つ以上、数字でない値）、ルールの評価、Accounting の増分（Gigawords、累計の減少、同じ値の再送、順序の誤り）、日本時間の日の割り当て、重複応答のキャッシュ（`radiussrv.Guard`）、取得先の登録簿の読み直し（形の誤り、使用中の取得先の削除）、取得先の応答の分類（契約 §9.3）、管理API の入力の検査と `cause`、監査ログのファイル（日の区切り、圧縮、削除）。
- Valkey の Lua（加入者、Accounting）は miniredis で走らせる。miniredis の Lua（gopher-lua）と本物の Valkey 9.1.2 で同じに動くことは、段階 2-3・2-4 で手元の compose で確かめた（設計概要 §17.1）。
- 偽物の作り方: 使う側のインターフェースをメモリーで実装する（`internal/auth/engine`、`internal/acct/processor` の試験）。gomock は `internal/auth/server` のハンドラーの試験（`internal/auth/mocks`）だけに残す。新しい試験では gomock を使わない。
- 時刻に依る処理は、時刻を引数で渡して固定する。miniredis の時計（TTL や Sorted Set の期限）と試験の時刻がずれないようにする。

### 2.2 結合

- **auth**: RADIUS のパケットを本物の UDP で送り、EAP の処理・Valkey（miniredis）・取得先のクライアント（mTLS）・偽の取得先（`internal/auth/source/sourcetest`。契約どおりに応え、受けた要求と返したベクターを記録する）までを通す。EAP-AKA・EAP-AKA' の成功と再同期、拒否する IMSI で取得先を呼ばないこと、Accept の属性とセッション、Accept の前の状態の再確認、EAP の Identity からの IMSI。
- **acct**: Accounting を本物の UDP で送り、利用の集計とセッションの更新、セッションのない Accounting、Valkey に届かないときに応答しないこと、索引の掃除。
- **radiussrv**: 本物の UDP で、応答の直後の再送がキャッシュから返ること、停止のときに処理中の要求の応答を待つこと（段階 2-6 の M11 で、直す前のコードで落ちることを確かめた試験）。
- **admin**: `net/http/httptest` で管理API の口（加入者、状態、一括取得、セッションの絞り込み、利用の取り出し、`/clients`・`/sources`・`/status`・`/audit-logs`）。
- **コマンド**: `client`・`admin-cert`・`fingerprint`・`sources check`。
- 本物の aka-vecgen との結合は、Go の試験ではなく検証機の通しで行う。

### 2.3 compose の通し（CI）

`.github/workflows/ci.yml` のジョブ「README の手順の通し確認」が、README の「起動手順」をそのまま流す: 取得先の登録簿と証明書・管理クライアントのピン・管理API のサーバー証明書を作り、`docker compose up --wait` で healthy になること、`healthcheck`、管理API（`/status`・`/clients`・`/sources`・加入者の登録）、登録していない管理クライアントを TLS で断ること、Valkey のバックアップと戻し（`scripts/`）、監査ログの日ごとのファイル。README の手順を変えたら、このジョブも直す。

### 2.4 検証機の通し

段階の終わりに、検証機で本物の部品を組み合わせて通す。段階 2 の終わりは aka-mvpset の `verify/stage2/`（29 項目。2026-10-29 にすべて通った）:

| 群 | 内容 |
|---|---|
| E | EAP-AKA・EAP-AKA' の成功（Class・VLAN・Session-Timeout）、両方の再同期 |
| R | 拒否（inactive、terminated、aka-radius にいない加入者、aka-vecgen にいない加入者、別のテナントのエッジ、刻印のない要求、刻印を信頼しないクライアント） |
| A | Accounting（Start・Interim の再送・Stop、Gigawords）と利用の集計・セッション |
| O | 運用（`/sources` と aka-vecgen の突き合わせ、`sources check`、`SIGHUP`、遮断器、続けて 20 回、再起動、バックアップと戻し、Fluent Bit、監査ログ、healthcheck） |

刻印はエッジの代わりの radsecproxy（Debian 13 の 1.11.2。UDP で受けて UDP で送る）で付け、Accounting と刻印のない要求は radclient で送る（S-01 eapaka_test利用ノウハウ）。

## 3. 合格の基準

| 項目 | 基準 |
|---|---|
| 試験 | すべて通る（`make test-race`） |
| カバレッジ | 全体で 80% 以上を目安にする（2026-10-29 の時点で 83%）。中心のパッケージ（`internal/auth/engine`・`eap`・`source`、`internal/acct/processor`・`store`、`internal/subscriber`、`internal/radiussrv`、`internal/admin/api`）は 85% 以上を目安にする。サーバーの組み立て（各 `run.go`）は低くてよい |
| 静的解析 | `gofmt -l .` が空、`make vet`・`make lint` が誤りなし |
| 脆弱性 | `make vulncheck` で、呼び出される既知の脆弱性がない |
| 不具合の直し | 直す前のコードで落ちる試験を足す（例: 段階 2-5 の K16 の `TestGuard_CachesBeforeSending`、2-6 の M11 の UDP の試験） |

## 4. CI

| ワークフロー | いつ | 内容 |
|---|---|---|
| `.github/workflows/ci.yml` | `main`・`develop` への push と PR | ジョブ build-and-test（`gofmt -l .` → `make build` → `make vet` → golangci-lint v2.14.0 → `make test-race`）、ジョブ「イメージと compose の設定」（イメージ `aka-radius` のビルドとサブコマンドなしの終了コード 2、`docker compose config` と重ね合わせ、`VALKEY_PASSWORD` が空なら断ること）、ジョブ「README の手順の通し確認」（2.3） |
| `.github/workflows/govulncheck.yml` | 同上と毎週月曜、手動 | `make vulncheck` |

- Go の版は `go.mod` から取る。第三者の Action はコミットの SHA で固定する。
- feature から develop へマージした後は、develop の CI も確かめる（PR の CI では通り、マージの後の develop で落ちたことがある。段階 2-5 の K16、2-6 の M11）。

## 5. 開発の流れ

1. 手元で `make fmt`・`make build`・`make vet`・`make lint`・`make test` を通す（E-02 §8）。
2. feature ブランチを push して PR を作り、CI を通す。
3. develop にマージした後、develop の CI を確かめる。
4. 段階の終わりに、検証機の通しを行う（2.4）。
