# O-05 ログ解析ガイド (r28)

## 1. 概要

- 目的: aka-radius のノードで、ログから認証・Accounting・管理API の動きをたどり、障害の原因を絞り込む手順をまとめる。
- 対象: aka-radius を動かす運用者と、試験を行う人。
- 前提: 運用ガイドの手順で動いていること（ログは `deployments/logs_on_host/` に出る）。ノードに `lnav` と `jq` があること（Debian 13 は `apt install lnav jq`）。

| 文書 | 使い方 |
|---|---|
| D-04 ログ仕様設計書 | `event_id` の意味・レベル・項目、共通の項目、トレースID、監査ログの形。**本書は `event_id` の意味を写さない**ので、D-04 と並べて読む |
| 運用ガイド | 9 章（ログと監査ログ、logrotate）、12 章（症状ごとの確かめ）。本書はその先の、ログの読み方を書く |
| aka-vecgen の運用ガイド | aka-vecgen のログ（`vecgen.log`）の `event_id` |

## 2. ログのファイル

`deployments/logs_on_host/` の下（経路は D-04 §1）。以下の例は、`/opt/aka-radius/deployments/logs_on_host/` に置いたとする（置き場所に合わせて読み替える）。

| ファイル | 中身 | lnav の書式 |
|---|---|---|
| `auth.log` | RADIUS 認証、取得先と遮断器、取得先の登録簿 | `aka_radius_log` |
| `acct.log` | Accounting、利用の集計、セッションの掃除 | `aka_radius_log` |
| `admin.log` | 管理API、監査ログの写し（`AUDIT`）、ピン・証明書・登録簿の読み直し | `aka_radius_log` |
| `valkey.log` | Valkey（JSON でない行を Docker のログドライバーの記録に包んだもの） | なし |
| `vecgen.log`・`vecgen-valkey.log` | 同じ VPS の aka-vecgen とその Valkey（aka-vecgen の `compose.fluent-bit.yaml` を重ねたとき） | なし（jq で読む。5 章） |

- 前の日までのファイルは logrotate が `auth.log-20261028.gz` のように圧縮する（運用ガイド 9.1。2 週間持つ）。
- 監査ログの日ごとのファイルは `deployments/audit/` にある（9 章）。
- `docker compose logs auth` でも同じ行が見られる（Fluent Bit が止まっているときの確かめにもなる）。

## 3. lnav

### 3.1 書式を入れて開く

```bash
lnav -i /opt/aka-radius/deployments/lnav_formats/eap_aka_log.json   # 書式を入れる（~/.lnav/formats/installed/ に写る）
lnav -C                                                              # 書式の検査（誤りがなければ何も出ない）
lnav /opt/aka-radius/deployments/logs_on_host/{auth,acct,admin}.log  # 3 つを時刻順に並べて開く
```

- 書式の名前は `aka_radius_log`、当たるファイルは `auth.log`・`acct.log`・`admin.log`（`file-pattern`）。書式を直したら入れ直す。
- 圧縮したファイルは、lnav にそのまま渡せる（`lnav auth.log-20261028.gz`）。

### 3.2 よく使うキー

| キー | 動作 |
|---|---|
| `e` / `E` | 次の・前の ERROR の行 |
| `w` / `W` | 次の・前の WARN の行 |
| `/`・`n`・`N` | 正規表現で探す、次・前 |
| `g` / `G` | 先頭・末尾 |
| `1`〜`6`（`Shift` で戻る） | 10 秒・1 分・10 分・1 時間・1 日・次の日の区切りへ |
| `;` | SQL（3.4） |
| `:` | コマンド（3.3） |
| `p` | 選んだ行の項目を開いて見る |

### 3.3 絞り込み

```
:filter-expr :event_id = 'AUTH_SUCCESS'
:filter-expr :event_id LIKE 'AUTH_STAMP_%' OR :event_id = 'AUTH_POLICY_DENIED'
:filter-expr :trace_id = '<トレースID>'
:filter-expr :imsi = '440101234567890'
:filter-expr :log_level = 'error'
:set-min-log-level warning
:filter-out PKT_RECV
:reset-session
```

- 項目の値で正しく絞るには `:filter-expr` を使う（SQL の `WHERE` と同じ書き方で、項目は `:event_id` のように `:` を付ける。1 つだけ置けて、置き直すと替わる）。
- `:filter-in`・`:filter-out` は、画面の行の文字（`時刻 レベル app event_id [imsi] msg`）に正規表現で当てる。`:filter-in event_id AUTH_SUCCESS` のように項目の名前を書くと、どの行にも当たらない。
- `log_level` は小文字（`debug`・`info`・`warning`・`error`）。JSON の `WARN` は `warning` になる。
- `:reset-session` ですべての絞り込みを外す。

### 3.4 SQL

`;` で SQL を書く。表は書式の名前の `aka_radius_log` を使う。

| 表 | 中身 |
|---|---|
| `aka_radius_log` | 書式の当たった全部の行。書式の `value` の項目（`event_id`・`imsi`・`trace_id`・`tenant_id`・`source_id`・`nas_identifier`・`session_id`・`cause`・`latency_ms`・`http_status` など）を列として使える |
| `all_logs` | どの書式の行も入るが、`log_time`・`log_level`・`log_body` などの共通の列だけ |
| `logline` | カーソルのある 1 行だけ |

- `msg` は `log_body`、もとの JSON の行は `log_raw_text`（どちらも隠れた列。`SELECT *` に出ない）。
- `value` にない項目（`error`・`day`・`method`・`path` など）は `jget(log_raw_text, '/項目名')` で取る（`value` にある項目も、`jget` で取ってよい）。
- 絞り込みを置いていると、SQL もその行だけが相手になる。全部を数えるときは `:reset-session` してから。
- `log_time` はローカルの時刻。今と比べるときは `datetime('now', 'localtime', '-1 hour')` のように `'localtime'` を付ける。
- 列の一覧は `;SELECT name, type FROM pragma_table_xinfo('aka_radius_log')`。

### 3.5 書式を直すときの注意

`deployments/lnav_formats/eap_aka_log.json` を直すときに気をつけること（本PoC で分かったこと）。

- **書式の名前は `bunyan_log` より辞書順で前にする。** lnav は書式を名前の順に試し、JSON の行に広く当たる組み込みの `bunyan_log` が先だと、こちらの書式が使われない（`aka_radius_log` は `a` で始まるので先に試される）。
- **`timestamp-format` を書かない。** `%N` は 9 桁に決め打ちで当たるが、Go の `RFC3339Nano` は末尾の 0 を削るので桁が変わる。lnav の ISO 8601 の自動の読み取りに任せる。
- **`file-pattern` で当たるファイルを絞る。** `valkey.log` などに当てないため。ログのファイルを増やしたら足す。
- **`sample` を残す。** `lnav -C` が見本の行を読めるかを確かめるので、直したあとの誤りがすぐ分かる。

## 4. 認証の流れとログの順

### 4.1 成功するとき

1 回の認証のログは、同じ `trace_id`（State の値）を持つ（D-04 §4）。

```
PKT_RECV               Access-Request（EAP-Response/Identity）。trace_id を作る
EAP_IDENTITY_RECEIVED
（EAP_IDENTITY_MISMATCH）  EAP の Identity と User-Name が違うとき
   ── ここで加入者・状態・刻印・ルールを確かめる（当たると 4.2 の拒否）
   ── 取得先へ 1 回要求する（成功はログに出さない。aka-vecgen の側に AV_ISSUED）
EAP_CHALLENGE_SENT     eap_type（23 / 50）と source_id
PKT_RECV               Access-Request（AKA-Challenge の応答）
AUTH_SUCCESS           tenant_id・rule_index・nas_identifier・session_id
```

- 仮名や高速再認証の ID で始めた端末には、永続 ID を求める往復が 1 回増える（`PKT_RECV` が 1 行増える）。
- 再同期では、`EAP_CHALLENGE_SENT` の後に `PKT_RECV` と `EAP_RESYNC_CHALLENGE` が入り、もう 1 回 `PKT_RECV` が来て `AUTH_SUCCESS` になる。2 回目の同期の失敗は `AUTH_RESYNC_LIMIT`。
- エッジが応答を待てずに送り直すと、`AUTH_DUPLICATE_REPLAYED`（前の応答を送り直した）が `trace_id` なしで出る。多いときは auth の応答が遅い（取得先の遅れ、`RADIUS_OVERLOAD`）。

### 4.2 拒否するとき

| 段 | 出る `event_id` | 取得先を呼ぶか |
|---|---|---|
| パケットの検証 | `RADIUS_NO_SECRET`・`PKT_MA_INVALID`・`PKT_NO_EAP`（応答なし） | 呼ばない |
| Identity | `EAP_IDENTITY_INVALID`・`EAP_UNSUPPORTED_TYPE` | 呼ばない |
| ベクターを取る前の判定 | `AUTH_SUBSCRIBER_*`・`AUTH_STAMP_*`・`AUTH_POLICY_DENIED` | 呼ばない |
| 取得先 | `VECTOR_*` | 呼ぶ（`VECTOR_CIRCUIT_OPEN`・`VECTOR_SOURCE_*` は呼ばない） |
| 端末の応答 | `EAP_AUTH_REJECT`・`EAP_CLIENT_ERROR`・`AUTH_MAC_INVALID`・`AUTH_RES_MISMATCH`・`AUTH_RESYNC_LIMIT` | 呼んだ後 |
| Accept の前の状態 | `AUTH_SUBSCRIBER_INACTIVE`・`AUTH_SUBSCRIBER_TERMINATED`（2 回目） | 呼んだ後 |

拒否の理由ごとの数:

```sql
;SELECT event_id, count(*) AS cnt
 FROM aka_radius_log
 WHERE app = 'auth' AND log_level IN ('warning', 'error')
 GROUP BY event_id ORDER BY cnt DESC
```

認証の成功の割合（加入者・設定・端末による拒否を数える。内部の誤りは含めない）:

```sql
;SELECT
   sum(event_id = 'AUTH_SUCCESS') AS success,
   sum(event_id LIKE 'AUTH_SUBSCRIBER_%' OR event_id LIKE 'AUTH_STAMP_%'
       OR event_id IN ('AUTH_POLICY_DENIED', 'VECTOR_REJECTED', 'AUTH_MAC_INVALID',
                       'AUTH_RES_MISMATCH', 'AUTH_VERIFY_FAIL', 'AUTH_RESYNC_LIMIT', 'EAP_AUTH_REJECT')) AS rejected
 FROM aka_radius_log
 WHERE app = 'auth' AND log_level != 'debug'
```

### 4.3 NAS とテナントで見る

`src_ip` はどれもエッジのトンネルの IP なので、AP は `nas_identifier`、テナントは `tenant_id` で見る（D-04 §8）。

```sql
-- NAS ごとの成功と拒否
;SELECT nas_identifier, event_id, count(*) AS cnt
 FROM aka_radius_log
 WHERE event_id IN ('AUTH_SUCCESS', 'AUTH_POLICY_DENIED', 'AUTH_STAMP_MISSING')
    OR event_id LIKE 'AUTH_SUBSCRIBER_%'
 GROUP BY nas_identifier, event_id ORDER BY nas_identifier

-- nas_identifier を持たない拒否は、同じ trace_id の PKT_RECV から NAS を引く
;SELECT DISTINCT e.log_time, e.event_id, e.imsi, r.nas_identifier
 FROM aka_radius_log e
 JOIN aka_radius_log r ON r.trace_id = e.trace_id AND r.event_id = 'PKT_RECV'
 WHERE e.event_id IN ('AUTH_MAC_INVALID', 'AUTH_RES_MISMATCH', 'VECTOR_REJECTED', 'VECTOR_TEMPORARY_ERR')
 ORDER BY e.log_time

-- テナントごとの成功の数（1 時間ごと）
;SELECT strftime('%Y-%m-%d %H:00', log_time) AS hour, tenant_id, count(*) AS cnt
 FROM aka_radius_log WHERE event_id = 'AUTH_SUCCESS'
 GROUP BY hour, tenant_id ORDER BY hour, tenant_id
```

## 5. トレースID で aka-vecgen までたどる

auth は取得先への要求の `X-Trace-ID` にトレースID を入れる。aka-vecgen は同じ値をログの `trace_id` に出すので、1 回の認証を aka-radius と aka-vecgen の両方でたどれる。`vecgen.log` は lnav の書式が当たらないので、jq で読む。

1. auth のログでトレースID を見つける（IMSI や時刻から。`PKT_RECV` は `imsi` を持たないので、IMSI では `EAP_CHALLENGE_SENT`・`AUTH_SUCCESS`・拒否の行が出る）。

   ```sql
   ;SELECT log_time, trace_id, event_id, log_level
    FROM aka_radius_log
    WHERE app = 'auth' AND imsi = '440101234567890'
    ORDER BY log_time DESC LIMIT 20
   ```

2. そのトレースID の auth のログを全部出す。

   ```sql
   ;SELECT log_time, log_level, event_id, log_body, jget(log_raw_text, '/reason') AS reason
    FROM aka_radius_log WHERE trace_id = '<トレースID>' ORDER BY log_time
   ```

3. aka-vecgen の側を見る。

   ```bash
   cd /opt/aka-radius/deployments/logs_on_host
   jq -c 'select(.trace_id == "<トレースID>")' vecgen.log
   ```

   aka-vecgen が断ったときは、`AV_REJECTED` の `reason` に理由（加入者がいない・止めてある・許可のないクライアント・AUTS の誤りなど）が出る。aka-radius の側は、契約どおり 403 の固定の本文しか受けないので `VECTOR_REJECTED`（`http_status` 403）としか分からない。理由は aka-vecgen の側で見る。

- jq で aka-radius のログも同じように読める（`jq -c 'select(.trace_id == "…")' auth.log`）。圧縮したファイルは `zcat auth.log-20261028.gz | jq -c '…'`。
- aka-vecgen のログの `event_id` は aka-vecgen の運用ガイドにある。

## 6. Accounting と利用の集計を追う

acct は Accounting-Request ごとに 1 行の記録のログ（`ACCT_START`・`ACCT_INTERIM`・`ACCT_STOP`）を出す（受けたことだけのログはない）。`trace_id` はパケットごとなので、同じ接続は `acct_session_id`（Acct-Session-Id）か `session_id`（Class。認証の `AUTH_SUCCESS` の `session_id` と同じ）でつなぐ。

```sql
-- ある認証のセッションの Accounting（AUTH_SUCCESS の session_id で）
;SELECT log_time, event_id, tenant_id,
        jget(log_raw_text, '/delta_seconds') AS sec,
        jget(log_raw_text, '/delta_in_octets') AS in_oct,
        jget(log_raw_text, '/delta_out_octets') AS out_oct,
        jget(log_raw_text, '/tenant_source') AS tenant_source
 FROM aka_radius_log
 WHERE session_id = '<session_id>' ORDER BY log_time

-- 利用の集計に入らなかった・テナント 0 になったもの
;SELECT event_id, count(*) AS cnt FROM aka_radius_log
 WHERE event_id IN ('ACCT_IMSI_UNKNOWN', 'ACCT_TENANT_UNKNOWN', 'ACCT_USAGE_TOO_OLD',
                    'ACCT_SESSION_NOT_FOUND', 'ACCT_SEQUENCE_ERR', 'USAGE_COUNTER_RESET')
 GROUP BY event_id
```

- `delta_*` は前回の累計からの増分で、利用の集計に足した値である。同じ値の再送（`ACCT_DUPLICATE_*`）は足さない。
- `tenant_source` はテナントの出どころ。`stamp`（刻印）が普通で、`seen`・`session` は刻印が使えなかったとき、`none` はテナント `0`。
- 1 日の合計を手で確かめるときは、`day` で絞って `delta_*` を足し、`GET /admin/v2/usage?date=YYYY-MM-DD` と比べる（IMSI とテナントごと。`auth_ok` は auth の `AUTH_SUCCESS` の数）。
- acct が Valkey に書けないときは `VALKEY_CONN_ERR`（`acct_session_id`）を出し、応答しない。NAS が送り直すので、復旧すれば数えられる（エッジの再送が尽きたものは落ちる）。
- Accounting-On / Off は `ACCT_ON`・`ACCT_OFF`（`nas_ip_address`）だけを出す。

## 7. 症状ごとの調べ方

運用ガイド 12 章で当たりを付けたあと、次の順にログを見る。

### 7.1 どの認証も通らない

1. `PKT_RECV` が出ているか。出ていなければ、パケットが届いていない（エッジの設定、`RADIUS_UDP_BIND`、nftables）か、Fluent Bit が止まっている（`docker compose logs auth` で確かめる）。
2. `RADIUS_NO_SECRET`（`src_ip`）が出ていれば、その IP が RADIUS クライアントにない。`RADIUS_LIB_ERR` や応答なしが続くなら、共有シークレットの食い違い（Message-Authenticator が合わず `PKT_MA_INVALID`）。
3. `AUTH_STAMP_MISSING` ばかりなら、エッジが刻印を付けていないか、RADIUS クライアントの `trust_stamp` が `false`（DEBUG にすると `AUTH_STAMP_UNTRUSTED` が出る）か、Vendor-Id・Vendor-Type が違う（auth の起動のログの `stamp_vendor_id`・`stamp_vendor_type`）。
4. `VECTOR_CIRCUIT_OPEN`・`VECTOR_TEMPORARY_ERR` ばかりなら、取得先の障害（7.4）。
5. `SOURCES_LOADED` が `count` 0 の WARN なら、登録簿が空ですべて拒否している。

### 7.2 ある加入者だけ通らない

その IMSI で `warning`・`error` の行を出す（5 章の 1）。

| 出ているもの | 見るところ |
|---|---|
| `AUTH_SUBSCRIBER_NOT_FOUND`・`_INACTIVE`・`_TERMINATED` | aka-radius の加入者の登録と状態（`GET /admin/v2/subscribers/{imsi}`）。aka-ossbss の台帳との食い違いは毎日の突き合わせで直る |
| `AUTH_POLICY_DENIED` | 行の `tenant_id`・`nas_identifier`・`ssid` と、加入者の `rules` を比べる（どのルールにも 3 つ揃って一致しない） |
| `AUTH_STAMP_MULTIPLE`・`AUTH_STAMP_INVALID` | エッジの設定（刻印を 2 回付けている、値が数でない） |
| `VECTOR_REJECTED`（403） | aka-vecgen の側の状態と許可のクライアント（5 章の 3） |
| `VECTOR_REJECTED`（400・501、ERROR） | 設定の食い違い（`anId` を aka-vecgen が許していないなど）。`cause` を見る |
| `VECTOR_SOURCE_UNKNOWN` | 加入者の `sourceId` が登録簿にない（`GET /admin/v2/sources`） |
| `EAP_AUTH_REJECT` | 端末が AUTN を受け入れなかった（端末の鍵が取得先と違う、ネットワーク名の食い違い） |
| `AUTH_MAC_INVALID`・`AUTH_RES_MISMATCH` | 端末と取得先の鍵（Ki・OPc）の食い違い。EAP-AKA' では Identity とネットワーク名（`RADIUS_EAP_AKA_PRIME_NETWORK_NAME`）も |
| `EAP_IDENTITY_MISMATCH` の後に拒否 | 外側の名前と EAP の Identity の違い自体は問題ない（EAP の Identity を使う） |

### 7.3 再同期が続く

`EAP_RESYNC_CHALLENGE` の数と、その後に `AUTH_SUCCESS` になったかを見る。

```sql
;SELECT imsi, sum(event_id = 'EAP_RESYNC_CHALLENGE') AS resync,
        sum(event_id = 'AUTH_RESYNC_LIMIT') AS over_limit, sum(event_id = 'AUTH_SUCCESS') AS ok
 FROM aka_radius_log WHERE app = 'auth'
 GROUP BY imsi HAVING resync > 0 ORDER BY resync DESC
```

- 同じ IMSI で毎回再同期するなら、端末と取得先の SQN の方式の食い違い（aka-vecgen の運用ガイド）。
- `AUTH_RESYNC_LIMIT` は、再同期のあとのベクターも受け入れられなかった（再同期は 1 回まで）。取得先の鍵か SQN の食い違い。

### 7.4 取得先の障害と遮断器

```sql
;SELECT log_time, event_id, source_id, http_status, latency_ms,
        jget(log_raw_text, '/reason') AS reason, jget(log_raw_text, '/to') AS cb_to
 FROM aka_radius_log
 WHERE event_id LIKE 'VECTOR_%' OR event_id LIKE 'CB_%'
 ORDER BY log_time
```

- `CB_OPEN` は一時的な誤り（`VECTOR_TEMPORARY_ERR`・`VECTOR_CONTRACT_VIOLATION`）が 5 回続いたとき。開いている間は `VECTOR_CIRCUIT_OPEN` が出て、30 秒後に `CB_HALF_OPEN`、成功が続けば `CB_CLOSE`。
- `reason` が `timeout` なら、取得先の遅れか届かない（共有の Docker ネットワーク、aka-vecgen の負荷）。`latency_ms` が取得先の `timeout`（既定 3 秒）に近い。
- 遮断器の今の状態は `GET /admin/v2/sources` の `circuitBreaker`。
- 接続そのものを確かめるには `docker compose run --rm --no-deps auth sources check`（運用ガイド 3 章）。

### 7.5 遅い・送り直しが多い

| 出ているもの | 意味 |
|---|---|
| `AUTH_DUPLICATE_REPLAYED`・`ACCT_DUPLICATE_REPLAYED` が多い | エッジが 5 秒のうちに応答を受けられず送り直している。前の応答を返しているので害は小さいが、auth・acct が遅い |
| `RADIUS_OVERLOAD` | 同時に処理する要求が `RADIUS_MAX_INFLIGHT` を超え、応えずに捨てた（`dropped`）。取得先の遅れで処理が積み上がっていることが多い |
| `VECTOR_TEMPORARY_ERR`（`reason` が `timeout`） | 取得先が遅い |

管理API の遅さは `ADMIN_REQUEST` の `latency_ms` で見る。

```sql
;SELECT jget(log_raw_text, '/method') || ' ' || jget(log_raw_text, '/path') AS req,
        count(*) AS cnt, avg(latency_ms) AS avg_ms, max(latency_ms) AS max_ms
 FROM aka_radius_log WHERE event_id = 'ADMIN_REQUEST'
 GROUP BY req ORDER BY max_ms DESC LIMIT 20
```

### 7.6 Valkey の障害

- 起動のときに届かなければ `VALKEY_CONN_ERR` で終了し、compose が起動し直す。
- 動いている間に届かなくなると、決まった `event_id` はなく、処理ごとの誤りの `error` に出る: auth は `RADIUS_SECRET_ERR`・`EAP_CTX_*`・`AUTH_SUBSCRIBER_LOOKUP_ERR`・`SESSION_CREATE_ERR`、acct は `VALKEY_CONN_ERR`、admin は `ADMIN_ERROR`、healthcheck は `HEALTH_VALKEY_ERR`（コンテナが unhealthy になる）。
- 接続は次のコマンドのときに張り直すので、これらの行が止まれば戻っている。`valkey.log` と `docker compose logs valkey` も見る。

### 7.7 管理API と監査ログ

| 出ているもの | 意味 |
|---|---|
| `ADMIN_CLIENT_REJECTED` | 登録していない・期限外の・ない証明書の接続を断った。`fingerprint` をピンのファイルの値と比べる（運用ガイド 5.1） |
| `ADMIN_REQUEST` の `http_status` が 4xx | 呼び出し側の誤り。本文の `cause` は aka-provisioner の側のログで見る（`trace_id` で突き合わせる） |
| `ADMIN_ERROR` | 中の誤り（500）。`error` を見る |
| `*_RELOADED`・`*_RELOAD_ERR` | `SIGHUP` の読み直しの結果（ピン、サーバー証明書、登録簿） |
| `AUDIT_WRITE_ERR` | 監査ログを書けなかった（`to` が `stream` か `file`）。操作は成功している |

## 8. よく使うクエリ

```sql
-- レベルごと・アプリごとの行の数
;SELECT app, log_level, count(*) AS cnt FROM aka_radius_log GROUP BY app, log_level

-- 1 時間ごとの ERROR の数
;SELECT strftime('%Y-%m-%d %H:00', log_time) AS hour, app, count(*) AS cnt
 FROM aka_radius_log WHERE log_level = 'error' GROUP BY hour, app ORDER BY hour

-- 直近 1 時間の WARN 以上を event_id ごとに
;SELECT event_id, count(*) AS cnt FROM aka_radius_log
 WHERE log_level IN ('warning', 'error') AND log_time > datetime('now', 'localtime', '-1 hour')
 GROUP BY event_id ORDER BY cnt DESC

-- 1 分ごとの認証の成功（スループット）
;SELECT strftime('%Y-%m-%d %H:%M', log_time) AS minute, count(*) AS cnt
 FROM aka_radius_log WHERE event_id = 'AUTH_SUCCESS' GROUP BY minute ORDER BY minute
```

```bash
jq -r 'select(.event_id == "AUTH_SUCCESS") | .tenant_id' auth.log | sort | uniq -c
zcat acct.log-20261028.gz | jq -c 'select(.event_id == "ACCT_TENANT_UNKNOWN")'
```

## 9. 監査ログを読む

監査ログは admin が Valkey の Stream と日ごとのファイルに書く（形は D-04 §7）。ログの `AUDIT` の行は写しである。

```bash
cd /opt/aka-radius/deployments/audit
jq -c 'select(.target == "440101234567890")' audit-20261029.jsonl          # ある IMSI の操作
jq -r '[.time, .mgmtClient, .operator, .action, .target] | @tsv' audit-*.jsonl
zcat audit-20261028.jsonl.gz | jq -c 'select(.action == "subscriber.delete")'
```

- 管理API の `GET /admin/v2/audit-logs` は Stream を新しい順に返す（aka-provisioner を通して見る）。
- コマンドの操作は `mgmtClient` が `cli`。RADIUS クライアントの共有シークレットの変更は `detail` の `"secret":"changed"` で分かる（値は残らない）。
- 監査ログの `traceId` は管理API の `X-Trace-ID` と同じなので、`admin.log` の `ADMIN_REQUEST` と aka-provisioner のログにつながる。
