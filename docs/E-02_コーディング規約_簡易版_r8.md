# E-02 コーディング規約（簡易版）(r8)

## 1. 概要

aka-radius の Go のコードの書き方をそろえるための規約である。対象はリポジトリの Go のコードすべて（`cmd/aka-radius`、`internal/`）。迷ったら、まわりのコードの書き方に合わせる。

| 本書で扱わないこと | 参照先 |
|---|---|
| ログの形と `event_id` の一覧 | D-04 ログ仕様設計書 |
| 誤りの分類と、RADIUS・管理API での扱い | D-06 エラーハンドリング詳細設計書 |
| Valkey のキーと形 | D-02 Valkey データ設計仕様書 |
| 環境とツール | E-01 開発環境セットアップガイド |
| 試験の書き方 | T-01 テスト戦略書 |

## 2. 命名

Go の一般の慣習（Effective Go、Go Code Review Comments）に従う。

| 対象 | 規則 | 例（コードから） |
|---|---|---|
| パッケージ | 小文字の 1 語。名詞。アンダースコアとハイフンを使わない | `subscriber`、`sessions`、`radiussrv`、`envconf` |
| 型 | PascalCase。略語は大文字のまま | `Subscriber`、`Rule`、`EAPContext`、`ContextStore` |
| インターフェース | 1 つのメソッドなら動詞 + `er`、複数なら役割の名詞 | `ContextStore`、`Sources`、`SourceStatus` |
| 関数・メソッド | 動詞で始める。コンストラクタは `New…`。真偽値は `Is`・`Has`・`Valid` など | `NewStore`、`ParseLevel`、`(State).Valid` |
| 変数 | 短く。慣用の短い名前（`ctx`・`err`・`req`・`w`・`r`）を使う | — |
| 定数 | exported は PascalCase、unexported は camelCase。列挙は型と接頭辞をそろえる | `StateActive`、`causeUserNotFound` |
| センチネルエラー | `Err` で始める | `subscriber.ErrNotFound`、`clients.ErrExists` |
| ファイル | 小文字、区切りはアンダースコア。試験は `_test.go` | `guard.go`、`integration_test.go` |
| 環境変数 | `RADIUS_` で始める大文字（設計概要 §4） | `RADIUS_REQUEST_TIMEOUT` |

- RFC や 3GPP の名前（`K_encr`・`K_aut` など）はそのまま使ってよい（`.golangci.yml` で staticcheck の ST1003 を外している）。
- コメントとログのメッセージは日本語でよい。`event_id`・フィールド名・JSON の項目名は英語。

## 3. パッケージ構成

### 3.1 全体

1 つのモジュール `github.com/oyaguma3/aka-radius` に、コマンド 1 つと `internal/` のパッケージを置く（構成の一覧は README の「リポジトリ構成」）。

| 置き場所 | 役目 |
|---|---|
| `cmd/aka-radius` | サブコマンドの振り分け（`auth`・`acct`・`admin`）と、運用のコマンド（`client`・`sources check`・`admin-cert`・`fingerprint`・`healthcheck`）。サーバーの中身は持たず、各サーバーの `Run` を呼ぶ |
| `internal/auth`・`internal/acct`・`internal/admin` | サーバーごとのパッケージ。`run.go` の `Run` が設定の読み込み・ロガー・Valkey・待ち受けを組み立てる。下に `config`・`server`（ハンドラー）・`store` などの小さなパッケージを置く |
| `internal/` の共有パッケージ | 2 つ以上のサーバーかコマンドで使うもの（下の表） |

| 共有パッケージ | 内容 | 使う側 |
|---|---|---|
| `radiussrv` | RADIUS の受け口（待ち受け、共有シークレット、刻印、Message-Authenticator、Proxy-State、Status-Server、`Guard`） | auth・acct |
| `subscriber` | 加入者のデータ（Lua）とルールの評価 | auth・admin |
| `sessions` | セッションと索引 | auth・acct・admin |
| `usage` | 利用の集計のキー、足し込み、取り出し | auth・acct・admin |
| `clients` | RADIUS クライアント | radiussrv・admin・コマンド |
| `audit` | 監査ログ（Stream と日ごとのファイル） | admin・コマンド |
| `health` | ループバックの healthcheck の口 | auth・acct・admin |
| `envconf` | 環境変数の読み込みと共通の設定 | すべて |
| `logging` | ログのフィールド名、レベル、IMSI のマスク | すべて |
| `valkey` | Valkey のクライアントの作成 | すべて |

### 3.2 依存の向き

```
cmd/aka-radius ──> internal/auth・acct・admin ──> 共有パッケージ ──> 標準ライブラリ・外部依存
```

- 共有パッケージはほかの `internal/` のパッケージを読まない。例外は `radiussrv`（`envconf`・`logging`・`clients` を読む）。
- サーバーのパッケージどうしは読み合わない。例外は admin が `internal/auth/source` の登録簿の読み込み（`source.ReadInfos`。鍵は読まない）を使うこと。
- 環境変数を読むのは各サーバーの `config` と `envconf` だけにする。ほかのパッケージは設定の値を引数で受ける。
- 外部依存は増やさない（設計概要 §4 の一覧）。HTTP は `net/http`（メソッドつきの `ServeMux`）、JSON は `encoding/json/v2`、ログは `log/slog`、設定は標準ライブラリで読む。

## 4. 誤りの扱い

### 4.1 誤りの作り方

| 形 | 使いどころ | 例 |
|---|---|---|
| センチネルエラー（`errors.New`） | 呼ぶ側が種類で分けたいもの | `subscriber.ErrNotFound`、`ErrTerminated` |
| 誤りの型 | 分類と付随の情報を運ぶもの | `source.Error`（`Kind`・取得先の ID・HTTP の状態・`cause`）と `source.KindOf` |
| `fmt.Errorf("…: %w", err)` | 下の層の誤りに文脈を足すもの | Valkey の誤りを包む |

- 種類の判定は `errors.Is`・`errors.As` で行い、メッセージの文字列で比べない。
- 誤りのメッセージは英語の小文字で始め、句点を付けない。秘密の値（共有シークレット、鍵、認証ベクター）を入れない。

### 4.2 層ごとの役目

| 層 | 役目 |
|---|---|
| データ（`store`・共有パッケージ） | 誤りを包んで返す。ログは出さない |
| 処理（`engine`・`processor` など） | 結果を決め（拒否・応えない・誤りの応答）、`event_id` つきのログを出す。同じ誤りを層ごとに重ねて出さない |
| 受け口（`radiussrv`・管理API のハンドラー） | 応答を作る。パニックを拾ってログに出す |

- RADIUS では、誤りの多くは拒否（EAP-Failure の Access-Reject）にする。Valkey に書けないときの acct は応答を返さない。詳しくは D-06 エラーハンドリング詳細設計書。
- 起動のときの誤り（設定、Valkey、証明書、登録簿）は `event_id` つきのログを出して終了する。`SIGHUP` の読み直しの誤りは前の設定のまま続ける。

### 4.3 管理API の誤り

ProblemDetails（RFC 9457）で返し、`cause` を入れる（`internal/admin/api`）。`cause` の値と HTTP の状態の対応は D-13 管理API 詳細設計書と OpenAPI（`docs/openapi/admin-api.yaml`）が正。

## 5. 構造体タグと JSON

- JSON は `encoding/json/v2` を使う。タグは `json:"camelCase"` で、省ける項目は `omitzero`（例 `subscriber.Rule` の `vlanId`・`sessionTimeout`）。
- Valkey の Hash に入れる項目は snake_case（D-02 Valkey データ設計仕様書）。Go の構造体のタグではなく、読み書きのコードで項目名を書く。
- 環境変数のタグ（envconfig など）は使わない。`envconf` の関数（`String`・`Required`・`Bool`・`PositiveInt`・`Duration` など）で読み、範囲を確かめる。

## 6. インターフェース

- インターフェースは使う側のパッケージに、要るメソッドだけで定義する（例: 管理API の `Sources`・`SourceStatus`）。
- 試験のために作るのは、偽物（メモリーの実装）で差し替えたい所だけにする。gomock は `internal/auth/server` の試験（`internal/auth/mocks`）だけで、ほかはメモリーの偽物と miniredis を使う（T-01 テスト戦略書）。

## 7. ログ

- `log/slog` の JSON ハンドラーで、標準出力に書く。レベルは `RADIUS_LOG_LEVEL`（`DEBUG`・`INFO`・`WARN`・`ERROR`。既定 `INFO`）を `logging.ParseLevel` で読む。
- 要求の処理と、運用者が見るべき出来事には `event_id` を付ける（値と意味は D-04 ログ仕様設計書が正。新しい値を足したら D-04 も直す）。フィールド名は `logging` の定数（`trace_id`・`event_id`・`imsi`・`src_ip`・`error` など）を使う。
- 認証の 1 回の流れには `trace_id` を付ける（取得先への `X-Trace-ID` と同じ値）。
- IMSI は `logging` のマスクを通して出す（既定はマスクしない。`RADIUS_LOG_MASK_IMSI`）。
- 共有シークレット、認証ベクター（RAND・AUTN・XRES・CK・IK・MSK）、鍵、証明書の鍵はログに出さない。

| レベル | 使いどころ |
|---|---|
| DEBUG | 開発のときだけ見る詳しい経過 |
| INFO | 正常の出来事（認証の成功、起動、読み直し） |
| WARN | 続けられる異常（拒否、捨てたパケット、契約に合わない応答） |
| ERROR | 処理の失敗、調べるべきこと（Valkey に届かない、起動できない） |

## 8. 整形と静的解析

- `gofmt` で整形する（CI は `gofmt -l .` が空であることを確かめる）。import の整理は `goimports` でよい。
- `make vet` と `make lint`（golangci-lint v2。`.golangci.yml` で `govet`・`errcheck`・`staticcheck`・`unused`・`ineffassign`）を通す。
- コミットの前に `make fmt`・`make build`・`make vet`・`make lint`・`make test` を通す（CI は `make test-race`）。
- 依存を足したら `make vulncheck` も通す。
