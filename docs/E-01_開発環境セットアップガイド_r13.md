# E-01 開発環境セットアップガイド (r13)

## 1. 概要

aka-radius を手元で開発・試験するための環境と手順をまとめる。起動の手順、環境変数、取得先の登録簿、管理API の使い方は README に、ノードの運用は運用ガイド（`docs/operation-guide.md`）にあり、本書では繰り返さない。

| 参照先 | 内容 |
|---|---|
| README | 起動手順、環境変数の一覧、取得先の登録簿、RADIUS クライアント、管理API、試験の実行 |
| 運用ガイド | ノードの構成と置き場所、証明書、ログ、バックアップと戻し |
| 設計概要（`docs/design-overview.md`） | MVP の決定事項と段階の記録 |
| E-02 コーディング規約（簡易版） | パッケージの構成、エラーとログの書き方 |
| T-01 テスト戦略書 | 試験の層、CI、検証機の通し |

## 2. 前提

| ソフトウェア | 版 | 用途 |
|---|---|---|
| Go | 1.27.3（`go.mod` の `go` の行。CI もここから読む） | ビルドと試験 |
| Docker Engine と compose プラグイン | 29 系、v5 系 | イメージのビルド、compose での通し |
| golangci-lint | v2 系（CI は v2.14.0） | `make lint` |
| mockgen（`go.uber.org/mock`） | v0.6.0 | モックを作り直すときだけ |
| radclient（freeradius-utils）、eapaka_test | — | 手元の compose に RADIUS を送るとき（S-01 eapaka_test利用ノウハウ） |

主に Linux（WSL2 を含む）を想定する。`make test-race` は `CGO_ENABLED=1` と C コンパイラが要る（WSL で入っていなければ `make test` を使い、データ競合の検出は CI に任せる）。

## 3. リポジトリ

```bash
git clone https://github.com/oyaguma3/aka-radius.git
cd aka-radius
make build
```

- 1 つのモジュール `github.com/oyaguma3/aka-radius` で、コマンドは `cmd/aka-radius` の 1 つ（サブコマンド `auth`・`acct`・`admin` と運用のコマンド）。パッケージは `internal/` の下にある。構成は README の「リポジトリ構成」、依存の向きは E-02 §3。
- ブランチは `main` ← `develop` ← `feature/*`。feature から develop へは PR を squash でマージし、develop から main へは merge commit でマージする。
- 外部依存を足すときは `go get` の後に `go mod tidy` し、`git diff go.mod` で変更が残っていることを確かめる。依存は少なく保つ（設計概要 §4 の一覧）。

## 4. ビルド・試験・静的解析

`Makefile` のターゲットを使う（CI も同じものを呼ぶ）。

| ターゲット | 内容 |
|---|---|
| `make build` | `go build ./...` |
| `make test` | `go test ./...` |
| `make test-race` | データ競合の検出つき（CI と同じ） |
| `make test-cover` | カバレッジ（`cover.out`）と合計 |
| `make fmt`・`make vet` | `gofmt -w .`・`go vet ./...` |
| `make lint` | golangci-lint（設定は `.golangci.yml`。v2 の形式で `version: "2"` が要る） |
| `make vulncheck` | govulncheck（`golang.org/x/vuln/cmd/govulncheck@v1.9.0`） |
| `make clean` | 成果物とカバレッジのファイルを消す |

- 試験は Valkey も取得先も要らない。Valkey は miniredis（`github.com/alicebob/miniredis/v2`）、取得先は偽の取得先（`internal/auth/source/sourcetest`）を試験の中で立てる（T-01 テスト戦略書）。
- モックは `internal/auth/mocks`（`internal/auth/server` のハンドラーの試験が使う）だけである。インターフェース（`internal/auth/eap/types.go`）を変えたら、リポジトリの直下で作り直す。

```bash
mockgen -source=internal/auth/eap/types.go -destination=internal/auth/mocks/eap_mock.go -package=mocks
```

- ほかのパッケージの試験は、メモリーの偽物と miniredis で書く（新しいモックを足さない）。

## 5. イメージ

```bash
docker build -t aka-radius:dev .
docker run --rm aka-radius:dev   # 使い方を出して終了コード 2 で終わる
```

- auth・acct・admin は同じイメージで、サブコマンドで切り替える。ベースは `gcr.io/distroless/static-debian13:nonroot`（UID 65532）なので、シェルはない。マウントするファイルは UID 65532 で読めるようにする（README の「起動手順」）。
- ビルドの版は `RADIUS_VERSION`（compose の build の引数）で埋め込み、起動のログの `build` と `/status` に出る。
- 本番の VPS の上ではビルドしない。手元か CI でビルドし、`docker save | gzip` で送って `docker load` する。

## 6. 手元の compose で試す

README の「起動手順」のとおりに `deployments/` で起動する。手元で試すときは次に気をつける。

- **プロジェクト名を必ず変える**（`docker compose -p <名前> …`）。ディレクトリの名前（`deployments`）のままだと、同じ名前のボリューム `deployments_valkey_data` が手元に残っていれば、それを使ってしまう。`scripts/backup-valkey.sh`・`restore-valkey.sh` は素の `docker compose` を呼ぶので、`COMPOSE_PROJECT_NAME`・`COMPOSE_FILE` を渡す。
- 手元でほかの compose が 1812・1813・6379・24224・9444 番を使っていれば、重ね合わせのファイルで付け替える。例: auth・acct・admin の `ports: !override`（127.0.0.1 の別のポート）、valkey の `ports: !reset []`、Fluent Bit を使わないなら `logging: !override {driver: json-file}` にして `fluent-bit` を起動しない。
- 手元に `sudo` がなければ、UID 65532 で読み書きさせるファイル（鍵・ピン・`audit/`）は試す間だけ 644・777 にし、終わったら消す。UID 65532 が作ったファイルは、別のコンテナ（例 `docker run --rm -v ./audit:/a valkey/valkey:9.1.2 ls -l /a`）で読み、消す。
- 取得先の登録簿の証明書は `openssl req -x509 …` で作ってよい（auth は起動のときに証明書と鍵とサーバーの CA を読むだけで、取得先を呼ぶのは認証のときである）。手順は CI の「README の手順の通し確認」（`.github/workflows/ci.yml`）が同じことをしている。
- 本物の aka-vecgen とつなぐときは、aka-vecgen の compose を先に起動し、`docker-compose.aka-av.yml` を重ねて共有ネットワーク `aka-av` に入る（運用ガイド 3 章）。
- RADIUS を送るときは radclient か eapaka_test を使う。テナントの刻印（Vendor-Specific 32473/1）は radclient なら `Attr-26 = 0x00007ed901043432` の形で付けられる（値 "42" の例）。eapaka_test は刻印を付けられないので、エッジの代わりの radsecproxy を通す（S-01 eapaka_test利用ノウハウ）。送信元は compose のネットワークのゲートウェイ（例 172.19.0.1）になるので、その IP を `client add -trust-stamp true` で登録する。
- 終わったら `docker compose -p <名前> down -v` で片付ける。

## 7. デバッグ

- ログは JSON（`log/slog`）で、`event_id` で絞る（D-04 ログ仕様設計書、O-05 ログ解析ガイド）。手元で Fluent Bit を通さないときは `docker compose -p <名前> logs auth | jq 'select(.event_id=="AUTH_SUCCESS")'` のように読む。`RADIUS_LOG_LEVEL=DEBUG` で詳しく出る。
- 認証の 1 回の流れは `trace_id`（取得先への `X-Trace-ID` と同じ値）でたどる。
- コンテナの中で Valkey を見るときは `docker compose -p <名前> exec valkey valkey-cli -a "$VALKEY_PASSWORD" --no-auth-warning …`（キーは D-02 Valkey データ設計仕様書）。
- Delve は手元で直接動かすとき（`dlv debug ./cmd/aka-radius -- auth`）に使える。環境変数は README の「コンテナの中のアプリが読む環境変数」。distroless のイメージの中では使えない。
