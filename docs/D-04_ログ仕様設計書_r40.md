# D-04 ログ仕様設計書 (r40)

- 対象: aka-radius の auth・acct・admin が出すログ（`event_id` の一覧、共通の項目、トレースID、IMSI の扱い）と監査ログの形。
- 正: コード（`internal/`・`cmd/aka-radius/`）。ログの経路は `configs/fluent-bit/fluent-bit.yaml` と `deployments/docker-compose.yml`、lnav の書式は `deployments/lnav_formats/eap_aka_log.json`。
- 関連: 設計概要（§13 ログと監査ログ）、運用ガイド（9 章 ログと監査ログ、12 章 障害時の確かめ）、O-05 ログ解析ガイド（調べ方）、D-06 エラーハンドリング詳細設計書（誤りのときの応答）。

## 1. ログの経路

| 段 | 内容 |
|---|---|
| 生成 | Go の `log/slog` の `JSONHandler` で、標準出力に 1 行 1 つの JSON を書く |
| 収集 | Docker のログドライバー `fluentd`（`fluentd-async`）で Fluent Bit（127.0.0.1:24224）に送る。タグは `app.auth`・`app.acct`・`app.admin`・`app.valkey` |
| 振り分け | Fluent Bit が `app.*` の `log` を JSON として読み直し、タグごとのファイルに書く（`logs_on_host/` の `auth.log`・`acct.log`・`admin.log`・`valkey.log`） |
| aka-vecgen | 同じ VPS の aka-vecgen は、aka-vecgen の `compose.fluent-bit.yaml` を重ねると同じ Fluent Bit に送る（`vecgen.log`・`vecgen-valkey.log`）。形は aka-vecgen の文書による |
| 保管 | ホストの logrotate で日ごとに圧縮し、ノードで 2 週間持つ。監視用の PC が取りに行く（運用ガイド 9.1） |

- Valkey のログは JSON でないので、`valkey.log` には Docker のログドライバーの記録（`log` に Valkey の行）がそのまま入る。
- 本PoC にあった healthcheck のログの振り分け（`rewrite_tag`、`others.log`）はなくした。healthcheck の口は失敗したときだけログを出す（3.6）。
- 監査ログは Fluent Bit を通さず、admin が Valkey の Stream と日ごとのファイルに直接書く（7 章）。
- コマンド（`docker compose exec admin aka-radius …`）は JSON のログを出さない。結果は標準出力、誤りは標準エラーに文で出す（3.5）。

## 2. 共通の項目

| 項目 | 型 | 内容 |
|---|---|---|
| `time` | 文字列 | 時刻（RFC 3339、ナノ秒、コンテナのタイムゾーン） |
| `level` | 文字列 | `DEBUG` / `INFO` / `WARN` / `ERROR` |
| `msg` | 文字列 | 人が読む文（auth・acct の多くは日本語、admin と acct の記録の結果は英語）。照合には `event_id` を使う |
| `app` | 文字列 | `auth` / `acct` / `admin`（ロガーを作るときに付ける） |
| `event_id` | 文字列 | 機械で読む識別子（3 章）。起動・停止のログと、設定の読み込みの失敗のログは持たない |
| `trace_id` | 文字列 | 追跡の ID（4 章）。パケットや要求に結び付かないログ（遮断器・読み直し・掃除など）は持たない |

- 項目の名前の定数は `internal/logging/fields.go`。よく使う項目: `src_ip`（RADIUS の送信元。エッジのトンネルの IP）、`imsi`、`nas_identifier`、`tenant_id`、`source_id`、`error`、`latency_ms`、`http_status`。
- 数として出す項目: `code`（RADIUS の Code）、`eap_type`（23 は EAP-AKA、50 は EAP-AKA'）、`subtype`、`acct_status_type`、`tenant_id`、`rule_index`、`resync_count`、`http_status`、`latency_ms`、`count`、`delta_*`、`event_timestamp`（UNIX 秒）。IMSI・ID・16 進の値は文字列にする。
- 本PoC と同じく、ソースの位置（`source`）は出さない。

起動のログ（`event_id` なし。INFO）:

| `app` | `msg` | 主な項目 |
|---|---|---|
| auth | `auth起動開始` | `build`、`listen_addr`、`log_level`、`sources_file`、`network_name`、`fallback_secret`（真偽）、`stamp_vendor_id`・`stamp_vendor_type`、`request_timeout_ms`、`max_in_flight` |
| acct | `acct起動開始` | `build`、`listen_addr`、`log_level`、`fallback_secret`、`stamp_vendor_id`・`stamp_vendor_type`、`request_timeout_ms`、`max_in_flight` |
| admin | `starting admin` | `version`（管理API の版）、`build`、`listen_addr`、`log_level`、`node_name`、`admin_clients_file`、`audit_dir`・`audit_retention_days`・`audit_max_len`、`sources_file`、`health_addr` |

- auth と acct は、予備の共有シークレット（`RADIUS_FALLBACK_SECRET`）が設定されていると、起動のときに WARN を 1 行出す（`event_id` なし）。
- 刻印の Vendor-Id と Vendor-Type は、エッジの設定と合っているかを確かめられるように起動のログに出す（設計概要 §8.3）。
- 停止のときは、シグナルの受信と停止の完了を INFO で出す（`event_id` なし）。

## 3. `event_id` の一覧

- 「コンテナ」は、そのログを出すサービス。auth のログは、特記がなければ `trace_id` を持つ。
- 「結果」は、そのときの応答（Reject は EAP-Failure の Access-Reject。応答なしはパケットを捨てる）。詳しい扱いは D-06 エラーハンドリング詳細設計書。
- `imsi` は `RADIUS_LOG_MASK_IMSI` に従う（5 章。既定はマスクしない）。

### 3.1 auth と acct に共通（RADIUS の受け口）

`internal/radiussrv` が出す。auth と acct の両方に入っている。

| `event_id` | レベル | 主な項目 | 内容・結果 |
|---|---|---|---|
| `RADIUS_NO_SECRET` | WARN | `src_ip` | 登録していない送信元（`client:{ip}` がない）で、予備の共有シークレットもない。応答なし |
| `RADIUS_SECRET_ERR` | WARN | `src_ip`、`error` | RADIUS クライアントを Valkey から読めない。予備の共有シークレットがあればそれで受け、なければ応答なし |
| `RADIUS_IP_EXTRACT_ERR` | WARN | `remote_addr` | 送信元の IP を取り出せない。予備の共有シークレットがあればそれで受ける |
| `RADIUS_LIB_ERR` | WARN | `error` | RADIUS のライブラリ（`layeh.com/radius`）の受信の誤り（パケットの形の誤りなど）。共有シークレットが決まらずに捨てたときは DEBUG（`RADIUS_NO_SECRET` が先に出ている） |
| `AUTH_DUPLICATE_REPLAYED`・`ACCT_DUPLICATE_REPLAYED` | INFO | `src_ip`、`code`、`identifier` | 重複応答のキャッシュに当たり、前の応答を送り直した（設計概要 §9）。`trace_id` は持たない |
| `AUTH_DUPLICATE_DROPPED`・`ACCT_DUPLICATE_DROPPED` | DEBUG | `src_ip`、`identifier` | 同じ要求を処理している最中に届いた再送を捨てた（最初の要求の応答がキャッシュに入れば、次の再送に返る） |
| `RADIUS_OVERLOAD` | WARN | `server`（`AUTH` / `ACCT`）、`max_in_flight`、`dropped` | 同時に処理する要求の上限（`RADIUS_MAX_INFLIGHT`）を超えたので、応えずに捨てた。1 秒に 1 行に間引き、`dropped` にその間に捨てた数を出す |
| `RADIUS_STATUS_OK` | DEBUG | `trace_id`、`src_ip` | Status-Server に応えた |
| `PKT_SEND_ERR` | ERROR | `trace_id`、`error` | 応答を送れない（重複応答の送り直しでは `trace_id` なし） |
| `SYS_PANIC` | ERROR | `src_ip`、`code`、`panic`、`stack` | パケットの処理中のパニックを回復した。そのパケットには応えず、プロセスは続ける |
| `SYS_LISTEN_ERR` | ERROR | `addr`、`error` | RADIUS の口か healthcheck の口で待ち受けられない、または停止のシグナルの前に止まった。プロセスは終了する（compose の `restart` で起動し直す） |
| `VALKEY_CONN_ERR` | ERROR | `error` | 起動のときに Valkey に届かない。プロセスは終了する（acct の実行中の使い方は 3.3） |

#### 3.2.3 ベクターを取る前の判定

最初の要求で、加入者 → 状態 → 刻印 → ルールの順に確かめる（設計概要 §8.1）。どれかに当たれば、取得先を呼ばずに Reject。状態は Accept の前にもう一度確かめ、そのときも同じ `event_id` を出す。

| `event_id` | レベル | 主な項目 | 内容 |
|---|---|---|---|
| `AUTH_SUBSCRIBER_NOT_FOUND` | WARN | `imsi`、`nas_identifier` | 加入者（`sub:{imsi}`）がない |
| `AUTH_SUBSCRIBER_INACTIVE` | WARN | `imsi`、`nas_identifier` | 状態が `inactive` |
| `AUTH_SUBSCRIBER_TERMINATED` | WARN | `imsi`、`nas_identifier` | 状態が `terminated` |
| `AUTH_SUBSCRIBER_INVALID` | ERROR | `imsi`、`error` | 加入者のデータの形が違う（本PoC の形の `sub:` が残っているなど） |
| `AUTH_SUBSCRIBER_LOOKUP_ERR` | ERROR | `imsi`、`error` | 加入者を Valkey から読めない |
| `AUTH_STAMP_UNTRUSTED` | DEBUG | `src_ip` | 刻印を信頼しない送信元（`trust_stamp` が `0`）なので刻印を使わない（続けて `AUTH_STAMP_MISSING`） |
| `AUTH_STAMP_MISSING` | WARN | `imsi`、`src_ip`、`nas_identifier` | テナントの刻印がない |
| `AUTH_STAMP_MULTIPLE` | WARN | `imsi`、`src_ip`、`count` | 刻印が 2 つ以上ある |
| `AUTH_STAMP_INVALID` | WARN | `imsi`、`src_ip`、`stamp` | 刻印の値が 10 進の 1 以上の数でない |

#### 3.2.4 取得先と遮断器

取得先の誤りのログは、分かる範囲で `source_id`・`http_status`・`cause`（取得先の ProblemDetails）・`reason`（分類の理由。例 `timeout`）・`latency_ms`・`error` を持つ。どれも Reject。分類は認証ベクターAPI の契約 §9.3 と D-09 Auth Server 詳細設計書。

| `event_id` | レベル | 内容 |
|---|---|---|
| `VECTOR_REJECTED` | WARN / ERROR | 取得先が断った。403（加入者がいない・止めてある・許可がない・AUTS の誤り）は WARN。400・501 など設定の食い違いは ERROR。遮断器には数えない |
| `VECTOR_TEMPORARY_ERR` | ERROR | 一時的な誤り（タイムアウト、接続できない、5xx）。遮断器に数える |
| `VECTOR_CONTRACT_VIOLATION` | ERROR | 応答が契約に合わない（要素の数・`avType`・値の長さ）。遮断器に数える |
| `VECTOR_CIRCUIT_OPEN` | ERROR | 遮断器が開いているので取得先を呼ばなかった |
| `VECTOR_SOURCE_UNKNOWN` | WARN | 加入者に取得先がない、または登録簿にない取得先を指している。取得先は呼ばない |
| `VECTOR_SOURCE_LOOKUP_ERR` | ERROR | 加入者の取得先を Valkey から読めない |
| `VECTOR_UNKNOWN_ERR` | ERROR | 上のどれでもない誤り |

| `event_id` | レベル | 主な項目 | 内容 |
|---|---|---|---|
| `CB_OPEN` | WARN | `source_id`、`from`、`to` | 取得先の遮断器が開いた（一時的な誤りが 5 回続いた） |
| `CB_HALF_OPEN` | INFO | 同上 | 開いてから 30 秒たち、半開きになった |
| `CB_CLOSE` | INFO | 同上 | 半開きで成功が続き、閉じた |
| `SOURCES_STATUS_WRITE_ERR` | WARN | `error` | 遮断器の状態を `stat:sources` に書けない（書けない間の最初の 1 回だけ） |

#### 3.2.5 認証の成功

| `event_id` | レベル | 主な項目 | 内容・結果 |
|---|---|---|---|
| `AUTH_SUCCESS` | INFO | `imsi`、`tenant_id`、`rule_index`、`nas_identifier`、`session_id` | Access-Accept を返した。`session_id` は Class に入れたセッションの UUID |
| `SESSION_CREATE_ERR` | ERROR | `error` | セッションを書けない。Reject |

#### 3.2.6 取得先の登録簿

| `event_id` | レベル | 主な項目 | 内容 |
|---|---|---|---|
| `SOURCES_LOADED` | INFO | `count`、`sources`（`id`・`name`・`base_url`・`timeout_ms`・`client_cert_expires`） | 起動のときに登録簿を読んだ。1 つもなければ WARN（すべての認証を拒否する） |

### 3.3 acct

acct のログは、`trace_id`（パケットごと）・`src_ip`・`nas_identifier` を持つ。記録の結果のログは、さらに `acct_session_id` を持つ。

| `event_id` | レベル | 主な項目 | 内容・結果 |
|---|---|---|---|
| `RADIUS_AUTH_ERR` | WARN | — | Request Authenticator（Status-Server では Message-Authenticator）が合わない。応答なし |
| `RADIUS_PARSE_ERR` | WARN | `reason` | 属性を取り出せない。応答なし |
| `RADIUS_UNKNOWN_CODE` | WARN | `code` または `acct_status_type` | Accounting-Request・Status-Server 以外の Code、または扱わない Acct-Status-Type。応答なし |
| `ACCT_START`・`ACCT_INTERIM`・`ACCT_STOP` | INFO | `imsi`、`tenant_id`、`tenant_source`、`session_id`、`day`、`delta_seconds`・`delta_in_octets`・`delta_out_octets` | 記録した。`tenant_source` はテナントの出どころ（`stamp`・`seen`・`session`・`none`）、`day` は集計の日（日本時間の `yyyymmdd`）、`delta_*` は前回の累計からの増分（設計概要 §10.2） |

| `ACCT_IMSI_UNKNOWN` | WARN | `user_name` | IMSI が分からない（セッション・重複の判定のキー・User-Name のどれからも）。集計しない |

| `SESSION_SWEEP_ERR` | ERROR | `error` | 索引の掃除に失敗した |

### 3.4 admin（管理API）

| `event_id` | レベル | 主な項目 | 内容・結果 |
|---|---|---|---|
| `ADMIN_REQUEST` | INFO | `trace_id`、`method`、`path`、`http_status`、`latency_ms`、`mgmt_client`、`operator`、`src_ip` | 要求を処理した（1 要求に 1 行）。`mgmt_client` は管理クライアントの識別名、`operator` は `X-Operator-Id` |
| `ADMIN_ERROR` | ERROR | `trace_id`、`method`、`path`、`error` | 中の誤り（Valkey に書けないなど）。500（`SYSTEM_FAILURE`）を返す |
| `ADMIN_CLIENT_REJECTED` | WARN | `reason`、`fingerprint`、`src_ip` | 登録していない・期限外の・ない証明書の接続を TLS のハンドシェイクで断った。登録の誤りは `fingerprint` と比べて確かめる |
| `AUDIT` | INFO | `trace_id`、`operator`、`mgmt_client`、`action`、`target`、`detail` | 監査ログを書いた（7 章の写し） |
| `AUDIT_WRITE_ERR` | ERROR | `to`（`stream` / `file`）、`trace_id`、`action`、`target`、`error` | 監査ログを書けない。操作は成功のまま |
| `AUDIT_MAINTAIN_ERR` | ERROR | `error` | 日ごとのファイルの圧縮か削除に失敗した（起動のときと 1 時間ごと） |
| `AUDIT_DIR_ERR` | ERROR | `error` | 起動のときに監査ログのディレクトリに書けない。プロセスは終了する |
| `ADMIN_CLIENTS_LOADED`・`ADMIN_CLIENTS_RELOADED` | INFO | `names`、`fingerprints` | 管理クライアントのピンを読んだ・`SIGHUP` で読み直した |
| `ADMIN_CLIENTS_LOAD_ERR` | ERROR | `file`、`error` | 起動のときにピンのファイルがない・読めない・形が違う・1 つもない。プロセスは終了する |
| `ADMIN_CLIENTS_RELOAD_ERR` | ERROR | `error` | 読み直せない。前のピンのまま続ける |
| `SERVER_CERT_LOADED`・`SERVER_CERT_RELOADED` | INFO | `subject`、`dns_names`、`not_after`、`fingerprint` | 管理API のサーバー証明書を読んだ・読み直した |
| `SERVER_CERT_LOAD_ERR` | ERROR | `cert`、`key`、`error` | 起動のときに証明書か鍵が読めない・組が合わない。プロセスは終了する |
| `SERVER_CERT_RELOAD_ERR` | ERROR | `error` | 読み直せない。前の証明書のまま続ける |
| `SOURCES_LOADED`・`SOURCES_RELOADED` | INFO | `count`、`ids` | 取得先の登録簿（ID と証明書の期限だけ。鍵は読まない）を読んだ・読み直した |
| `SOURCES_LOAD_ERR` | ERROR | `sources_file`、`error` | 起動のときに登録簿が読めない。プロセスは終了する |
| `SOURCES_RELOAD_ERR` | ERROR | `error` | 読み直せない。前の登録簿のまま続ける |
| `SYS_PANIC` | ERROR | `method`、`path`、`panic` | 要求の処理中のパニックを回復した |
| `SYS_LISTEN_ERR` | ERROR | `addr`、`error` | 管理API か healthcheck の口で待ち受けられない。プロセスは終了する |

- 起動のときに Valkey に届かないときは、`VALKEY_CONN_ERR`（ERROR。`addr`、`error`）を出して終了する（auth・acct と同じ ID。3.1）。

### 3.5 コマンド

`cmd/aka-radius` のコマンド（`client`・`sources check`・`admin-cert`・`fingerprint`・`healthcheck`）は、JSON のログを出さない。

- 結果は標準出力、誤りは標準エラーに文で出し、終了コードで成否を返す。
- 書き込みのコマンド（`client add / update / remove`、`admin-cert create`）は監査ログを書く（7 章。管理クライアント `cli`）。書けなかったときだけ、標準エラーに文で出す（`AUDIT` の行は出さない）。
- `admin-cert create` は Valkey に届かないときも、日ごとのファイルにだけ監査ログを書く。

### 3.6 healthcheck の口（auth・acct・admin に共通）

| `event_id` | レベル | 主な項目 | 内容 |
|---|---|---|---|
| `HEALTH_VALKEY_ERR` | WARN | `error` | `GET /healthz` で Valkey の PING に失敗した（503 を返す）。成功はログに出さない |
| `HEALTH_SERVE_ERR` | ERROR | `error` | healthcheck の口が止まった |

## 4. トレースID

| コンテナ | `trace_id` の決め方 | つながり |
|---|---|---|
| auth | State 属性が UUID の形なら、その値をそのまま使う。なければ（最初の Access-Request、Status-Server）新しい UUID を作る | 同じ値を会話のキー `eap:{traceId}` と Access-Challenge の State に使うので、1 回の認証のログ（各パケットの `PKT_RECV` を含む）を 1 つの `trace_id` でたどれる。取得先への要求の `X-Trace-ID` にも入れるので、aka-vecgen のログの `trace_id` と同じ値になる |
| acct | パケットごとに新しい UUID | 認証との対応は Class（`session_id`・`class_uuid`）でとる |
| admin | `X-Trace-ID`（表示できる ASCII で 64 文字まで）があればその値、なければ 16 バイトの乱数の 16 進 | 応答の `X-Trace-ID` で返し、`ADMIN_REQUEST`・`ADMIN_ERROR`・監査ログの `traceId` に残す。aka-provisioner のログと突き合わせる |

- State が UUID の形でないときは、受け口のログは新しい UUID、EAP の処理のログ（`EAP_CTX_NOT_FOUND`）は State の値になり、一致しない（その会話はないので Reject になる）。
- 遮断器（`CB_*`）・読み直し・掃除・重複応答の送り直しのログは、`trace_id` を持たない。時刻と `source_id`・`src_ip` で突き合わせる。

## 5. IMSI と出さないもの

### 5.1 IMSI

| 環境変数 | 既定 | 内容 |
|---|---|---|
| `RADIUS_LOG_MASK_IMSI` | `false` | `true` にすると、ログの `imsi` を先頭 6 桁と末尾 1 桁を残して `*` にする（例 `440101********0`） |

- 既定でマスクしないのは、調査と解析のトレーサビリティを優先するため（MVP の決定事項 26。aka-vecgen も同じ）。ログを取りに行く監視用の PC の保管とアクセスできる人も、ノードと同じく限る（運用ガイド 9 章）。
- EAP の Identity と User-Name（`identity`・`user_name`）も同じ設定に従い、`@` より前の IMSI の部分をマスクする（`internal/logging/masking.go` の `MaskUserName`）。
- 監査ログの `target`（IMSI）はマスクしない。

### 5.2 出さないもの

次の値は、どのレベルのログにも監査ログにも出さない。

- RADIUS の共有シークレット（監査ログの `detail` も `"secret":"changed"` だけ）
- 認証ベクター（RAND・AUTN・XRES・CK・IK・CK'・IK'）と、それから導いた鍵（K_aut・MSK・MS-MPPE-*-Key）
- 取得先のクライアント証明書の鍵、管理API のサーバー証明書の鍵（登録簿と証明書のファイルのパスもログに出さない。出すのは主体名・期限・フィンガープリント）

## 6. ログレベル

| 環境変数 | 既定 | 内容 |
|---|---|---|
| `RADIUS_LOG_LEVEL` | `INFO` | 出す最低のレベル（`DEBUG` / `INFO` / `WARN` / `ERROR`。大文字と小文字を区別せず、`WARNING` も受ける。知らない値と空は `INFO`）。auth・acct・admin に共通（`internal/logging/level.go`） |

- `DEBUG` のときだけ出るもの: `RADIUS_STATUS_OK`、Status-Server の `PKT_RECV`、`AUTH_DUPLICATE_DROPPED`・`ACCT_DUPLICATE_DROPPED`、`AUTH_STAMP_UNTRUSTED`、`ACCT_DUPLICATE_STOP`、共有シークレットが決まらずに捨てたときの `RADIUS_LIB_ERR`。
- 本番は `INFO`。

## 7. 監査ログ

管理API とコマンドの変更の操作を、Valkey の Stream と日ごとのファイルに書く（`internal/audit`。設計概要 §13）。ログの `AUDIT` の行は写しで、正本は Stream とファイルである。

| 置き場所 | 形 | 持つ期間 |
|---|---|---|
| Valkey の Stream `audit` | 項目 `operator`・`mgmt_client`・`action`・`target`・`detail`・`trace_id`。時刻はエントリID のミリ秒 | `RADIUS_AUDIT_MAX_LEN` 件（既定 10000。おおよそ） |
| 日ごとのファイル `audit-YYYYMMDD.jsonl`（`RADIUS_AUDIT_DIR`） | 1 行 1 つの JSON。項目 `time`（日本時間、RFC 3339）・`operator`・`mgmtClient`・`action`・`target`・`detail`（JSON）・`traceId`・`streamId` | `RADIUS_AUDIT_RETENTION_DAYS` 日（既定 14）。前の日までのファイルは gzip で圧縮する |

- ファイルの日付は日本時間で区切る。形・圧縮・削除は aka-vecgen と同じ。
- `streamId` は Stream のエントリID（Valkey に書けなかったときは空）。ファイルと Stream を突き合わせられる。
- 管理API の操作は `mgmtClient` が管理クライアントの識別名、`operator` が `X-Operator-Id`。コマンドの操作は `mgmtClient` が `cli`、`operator` が `-operator`（既定 `cli`）。
- 読み出しは `GET /admin/v2/audit-logs`（Stream を新しい順。D-13 管理API 詳細設計書）。

| `action` | 操作 | `target` | `detail` |
|---|---|---|---|
| `subscriber.create` | `POST /subscribers` | IMSI | 状態・取得先・ルール |
| `subscriber.update` | `PATCH /subscribers/{imsi}` | IMSI | 変えた項目の前と後 |
| `subscriber.state` | `PUT /subscribers/{imsi}/state` | IMSI | 状態の前と後、理由（あれば）、変わらなかったときは `unchanged` |
| `subscriber.reinstate` | `POST /subscribers/{imsi}/reinstate` | IMSI | 状態の前と後、理由 |
| `subscriber.delete` | `DELETE /subscribers/{imsi}` | IMSI | 消したときの状態・取得先・ルール |
| `client.create`・`client.update`・`client.delete` | `client add / update / remove` | RADIUS クライアントの IP | 名前と `trustStamp`（変更は前と後）。共有シークレットは変えたときに `changed` とだけ書く |
| `admin-server-certificate.create` | `admin-cert create` | `aka-radius-admin`（証明書の主体名） | フィンガープリント・SAN（DNS 名と IP）・期限 |

- 読むだけの口とコマンドは監査ログに残さない。
- 本PoC の Admin-TUI の監査ログ（標準出力）と Provisioning API の `AUDIT_LOG`・`audit:prov` は、この 1 系統にまとめた。

## 8. NAS の識別

エッジ（radsecproxy）を通すので、`src_ip` はどれもエッジのトンネルの IP になる。AP を区別するには `nas_identifier` を見る。

| コンテナ | `nas_identifier` を持つログ |
|---|---|
| auth | `PKT_RECV`（Access-Request。Message-Authenticator の検証の前の値）、`AUTH_SUCCESS`、`AUTH_SUBSCRIBER_NOT_FOUND`・`AUTH_SUBSCRIBER_INACTIVE`・`AUTH_SUBSCRIBER_TERMINATED`、`AUTH_STAMP_MISSING`、`AUTH_POLICY_DENIED` |
| acct | すべての記録のログ（`ACCT_*`・`USAGE_*`） |

- ほかの auth のログは、同じ `trace_id` の `PKT_RECV` で NAS を特定する。
- テナントは `tenant_id`（刻印の値）で見る。NAS-Identifier は個人の情報ではないので、マスクしない。

## 9. lnav

ノードで読むときの書式は `deployments/lnav_formats/eap_aka_log.json`（書式の名前 `aka_radius_log`。`auth.log`・`acct.log`・`admin.log` に当たる）。入れ方と使い方は O-05 ログ解析ガイド。

- `value` には、絞り込みに使う識別子（`app`・`imsi`・`trace_id`・`event_id`・`source_id`・`tenant_id`・`src_ip`・`session_id`・`acct_session_id`・`cause`・`nas_identifier`・`mgmt_client`・`operator`・`action`・`target` など）と、数として集計する項目（`rule_index`・`delta_seconds`・`delta_in_octets`・`delta_out_octets` など）を定義している。定義していない項目も `jget(log_raw_text, '/項目名')` で取れる。
