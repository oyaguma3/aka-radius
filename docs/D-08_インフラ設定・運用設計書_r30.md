# D-08 インフラ設定・運用設計書 (r30)

## 1. 概要

### 1.1 目的

本書は、aka-radius をコンテナで動かすための構成（コンテナ、ネットワーク、マウント、公開先、Valkey、ログ）と、その設計の理由を定める。MVP セットでは、aka-radius はデータ面の VPS に aka-vecgen と並べて置く（aka-mvpset の要件と構成の概要 §5。以下「概要」）。

r29 までは本PoC（eapaka-radius-server-poc）のミニPC 1 台の構成（Ubuntu、UFW、Admin-TUI、vector-gateway・vector-api のコンテナ、`provisioning-api`）を書いていた。MVP の段階 2 で作りを改めたので、r30 で書き直した。

## 2. 配置

### 2.1 置き場所

| 項目 | 内容 |
|---|---|
| ノード | データ面の VPS（aka-vecgen と同じ）。Debian 13、Docker Engine と compose プラグイン |
| 大きさの目安 | 2 vCPU / 4 GB から始め、規模の試験（加入者 20 万件、セッション 20,000 件、ピーク 50 TPS）で決める（概要 §16） |
| イメージ | 手元か CI でビルドして送る。VPS の上ではビルドしない（ビルドにメモリーを多く使うため） |
| 冗長化 | しない（冗長化はエッジだけ。概要 §5） |

### 2.2 つながる相手と経路

```
[エッジ（radsecproxy）] ──RADIUS/UDP（サービス用の WireGuard）──> 1812・1813 ── auth・acct ─┐
[aka-provisioner] ──mTLS（サービス用の WireGuard）──────────────> 9444 ── admin ────────────┼── valkey
auth ──mTLS（共有ネットワーク aka-av）──> aka-vecgen 8443                                     │
各コンテナのログ ──fluentd のログドライバー（127.0.0.1:24224）──> fluent-bit ──> logs_on_host/ ┘
[運用者] ──SSH（運用用の WireGuard と踏み台）──> docker compose exec admin aka-radius …
[監視用の PC] ──（運用用の WireGuard）──> logs_on_host/・audit/ を取りに行く
```

- RADIUS クライアントはエッジ（のトンネルの IP）だけである。エッジは AP からの RadSec を受け、テナントの刻印（Vendor-Specific 32473/1）を付けて aka-radius に送る（概要 §8・§9）。
- エッジの radsecproxy の設定は radsec-edge の設計にある。段階 2 の通しでは、エッジの代わりの radsecproxy（aka-mvpset の `verify/stage2/`）で刻印を付けて確かめた。radsecproxy は `rewrite` のブロックを、それを使う `client` より前に書く。

### 2.3 公開先

| ポート | compose の公開先（既定） | 本番 | 理由 |
|---|---|---|---|
| 1812/udp（auth）・1813/udp（acct） | `RADIUS_UDP_BIND`（`127.0.0.1`） | サービス用の WireGuard のアドレス | エッジはトンネルの IP から送ってくる。インターネットには出さない |
| 9444/tcp（admin） | `RADIUS_ADMIN_BIND`（`127.0.0.1`） | サービス用の WireGuard のアドレス | aka-provisioner は管理面の VPS から WireGuard でつなぐ |
| 6379/tcp（valkey） | `127.0.0.1` | そのまま | ホストの上の調べもののため。ホストの外に出さない |
| 24224（fluent-bit） | `127.0.0.1` | そのまま | Docker のログドライバーがホストの `localhost:24224` に送るため |
| 9090/tcp（healthcheck） | 公開しない | そのまま | 各コンテナのループバックだけ（4.4） |

- 既定をループバックにしたのは、`.env` を書き忘れたまま起動しても外に出ないようにするため（段階 2-6）。
- Docker が公開したポートはホストのファイアウォール（UFW など）の規則を通らないので、送信元の絞り込みは nftables の `DOCKER-USER` で行う（1812・1813 はエッジのトンネルの IP、9444 は aka-provisioner）。規則は段階 5 の配置の文書で決める。
- 予備の共有シークレット `RADIUS_FALLBACK_SECRET` は空のままにする。空なら、登録していない送信元のパケットは捨てる（`RADIUS_NO_SECRET`）。設定すると、起動のログに WARN が出る。

## 3. コンテナ

### 3.1 一覧

| サービス | イメージ | 内容 | 待ち受け（コンテナの中） |
|---|---|---|---|
| `auth` | `aka-radius:${RADIUS_VERSION}`（サブコマンド `auth`） | RADIUS 認証、EAP-AKA / EAP-AKA'、取得先からの認証ベクターの取得 | `:1812/udp`、`127.0.0.1:9090` |
| `acct` | 同上（`acct`） | RADIUS Accounting、利用の集計、セッションの索引の掃除（1 時間ごと） | `:1813/udp`、`127.0.0.1:9090` |
| `admin` | 同上（`admin`） | 管理API 2.0.0、運用のコマンド、監査ログのファイルの圧縮と削除 | `:9444/tcp`、`127.0.0.1:9090` |
| `valkey` | `valkey/valkey:9.1.2` | データの保存先 | `:6379` |
| `fluent-bit` | `fluent/fluent-bit:4.2.8` | ログをアプリごとのファイルに書く | `:24224` |

- auth・acct・admin は同じイメージで、compose の `command` でサブコマンドを変える（設計概要 §4）。プロセスを分けたのは、Accounting の負荷や管理API の不具合が認証に及ばないようにするため。
- 運用のコマンド（`client`・`sources check`・`admin-cert`・`fingerprint`・`healthcheck`）も同じバイナリにある（設計概要 §12）。`client`・`admin-cert` は admin のコンテナ、`sources check` は auth のコンテナ（`docker compose run --rm --no-deps auth sources check`）で動かす。
- 本PoC の vector-gateway は auth に取り込み、vector-api と Admin-TUI はなくした（設計概要 §3.2）。

### 3.2 イメージ

- ビルドは Go 1.27.3 のイメージ、実行は `gcr.io/distroless/static-debian13:nonroot`（シェル、curl、pgrep を持たない。UID 65532 で動く。段階 2-5 の K11）。
- ビルドの版は compose の `RADIUS_VERSION` から渡し、起動のログと `/status` の `build` に出る。
- イメージの版はパッチ版まで書く（distroless は除く）。

### 3.3 マウントと持ち主

コンテナは UID 65532 で動くので、マウントするファイルとディレクトリはこの UID で読み書きできるようにする（README の「起動手順」）。

| ホスト（`deployments/` の下） | コンテナ | どこから | 読み書き | 中身 |
|---|---|---|---|---|
| `sources/` | `/etc/aka-radius/sources` | auth・admin | 読み取り専用 | 取得先の登録簿 `sources.json` と、取得先ごとのクライアント証明書・鍵・サーバーの CA（4.1）。鍵は 600 |
| `certs/admin/` | `/certs` | admin | 読み取り専用 | 管理API のサーバー証明書 `server.pem`・`server.key`。鍵は 600 |
| `secrets/admin-clients` | `/run/secrets/admin-clients` | admin | 読み取り専用（compose の secrets） | 管理クライアントのピン。600 |
| `audit/` | `/var/lib/aka-radius/audit` | admin | 読み書き | 監査ログの日ごとのファイル（6.4） |
| `logs_on_host/` | `/output_logs` | fluent-bit | 読み書き | アプリごとのログのファイル（6.2） |
| `../configs/fluent-bit/fluent-bit.yaml` | `/fluent-bit/etc/fluent-bit.yaml` | fluent-bit | 読み取り専用 | Fluent Bit の設定 |
| ボリューム `valkey_data` | `/data` | valkey | 読み書き | AOF とスナップショット |

- `sources/`（例のファイルのほか）、`certs/`、`secrets/`、`audit/`、`logs_on_host/*.log`、`.env` は git に入れない（`.gitignore`）。
- ピンのファイルは admin を一度でも起動する前に作る。ないと Docker が同じ名前のディレクトリを作る。
- 取得先の証明書と鍵を Docker の secrets でなくディレクトリのマウントで渡すのは、取得先の数が決まっておらず、登録簿からパスで指すため（段階 2-2 の B2。設計概要 §14）。
- ボリュームの名前は `<プロジェクト名>_valkey_data` になる。プロジェクト名はディレクトリの名前（`deployments`）が既定なので、同じホストで別の試しをするときは `docker compose -p <名前>` で分ける（ほかのプロジェクトのボリュームを使ってしまわないため）。

### 3.4 ネットワーク

| ネットワーク | 作る側 | 入るもの | 用途 |
|---|---|---|---|
| `default`（プロジェクトの既定） | この compose | すべて | コンテナの間（`valkey:6379` など） |
| `aka-av`（`AKA_SHARED_NETWORK`） | aka-vecgen の compose | auth（`docker-compose.aka-av.yml` を重ねたとき） | auth から `https://aka-vecgen:8443` に届く |
| `aka-radius-admin`（`RADIUS_ADMIN_SHARED_NETWORK`） | この compose | admin（別名 `aka-radius-admin`） | 同じホストの呼び出し側（試しと CI の aka-provisioner）から `https://aka-radius-admin:9444` に届く |

- 同じホストの別の compose のコンテナは、ホストの `127.0.0.1` に公開したポートに届かないので、共有ネットワークでつなぐ。
- 本番の aka-provisioner は別の VPS から WireGuard でつなぐので、`aka-radius-admin` は同じホストでの試しと CI のためのもの（段階 2-5 の K13）。
- `aka-av` は aka-vecgen が作るので、aka-vecgen を先に起動する。`.env` に `COMPOSE_FILE=docker-compose.yml:docker-compose.aka-av.yml` と書くと、素の `docker compose` でも重なる。別のホストの取得先なら重ねずに、登録簿の `baseUrl` を相手のアドレスにする。
- auth が共有ネットワークに入ると、ホストから送った RADIUS の送信元は共有ネットワークの側のゲートウェイになることがある。手元で試すときは、そのアドレスを RADIUS クライアントに登録する。

### 3.5 起動の順と依存

- auth・acct・admin は valkey の healthy を待って起動する（`depends_on` の `service_healthy`）。fluent-bit は独立に起動する。
- 起動のときに設定・ファイル・Valkey のどれかが読めないと、ログに `event_id`（`SOURCES_LOAD_ERR`・`ADMIN_CLIENTS_LOAD_ERR`・`SERVER_CERT_LOAD_ERR`・`AUDIT_DIR_ERR`・`VALKEY_CONN_ERR`・`SYS_LISTEN_ERR` など）を出して終了し、`restart: always` で起動し直す。表は運用ガイドの 2 章。
- aka-vecgen はこの compose の外にあるので、`depends_on` では待てない。aka-vecgen が止まっていても auth は起動し、取得先の遮断器が開く（D-09）。

### 3.6 healthcheck

| サービス | 方法 | 間隔・期限・回数・起動の猶予 |
|---|---|---|
| auth・acct・admin | `aka-radius healthcheck`（同じコンテナのループバックの口 `GET /healthz` に問い合わせ、口は Valkey に PING を 1 秒まで送る） | 30 秒・5 秒・3 回・10 秒 |
| valkey | `valkey-cli ping \| grep -q PONG`（パスワードは環境変数 `VALKEYCLI_AUTH`） | 10 秒・3 秒・3 回・5 秒 |
| fluent-bit | なし | — |

- 口は `RADIUS_HEALTH_ADDR`（既定 `127.0.0.1:9090`）。コンテナごとにネットワークの名前空間が分かれているので、3 つとも同じポートを使う（段階 2-5 の K10）。
- 本PoC は UDP と mTLS のため `pgrep` でしか確かめられず、待ち受けていなくてもプロセスがあれば healthy だった。口を足したので、distroless のイメージで確かめられる。
- 口は失敗のときだけログを出す（`HEALTH_VALKEY_ERR`）。本PoC の、ヘルスチェックのログを Fluent Bit で分ける設定（`rewrite_tag`）は要らなくなった。
- valkey の healthcheck で `PONG` を確かめるのは、`valkey-cli` が認証に失敗しても終了コード 0 で終わるため。パスワードを `-a` で渡さないのは、`ps` に出るため。

### 3.7 停止

| サービス | 止め方 | 待つ時間 |
|---|---|---|
| auth・acct | 新しいパケットを受けるのをやめ、処理中のパケットが応答を送り終えるのを待ってから待ち受けを閉じる（段階 2-6 の M11） | 5 秒まで（Docker の既定の猶予 10 秒の中） |
| admin | 処理中の要求を待つ | 10 秒まで。compose の `stop_grace_period` を 20 秒にし、強制終了と重ならないようにする |

- 更新で作り直すと auth・acct は数秒止まる。その間の要求はエッジが送り直す。重複応答のキャッシュはプロセスのメモリーにあるので、作り直すと消える（設計概要 §9）。

## 4. 取得先（aka-vecgen）とつなぐ配置

D-12（vector-gateway。廃止）の配置の話を、MVP の作りに合わせて取り込んだ。取得先のクライアントの作り（mTLS、遮断器、契約）は D-09 にある。

### 4.1 登録簿と証明書の置き場所

- 登録簿は `deployments/sources/sources.json`（`RADIUS_SOURCES_FILE`、既定 `/etc/aka-radius/sources/sources.json`）。項目は `id`・`name`・`baseUrl`・`clientCertFile`・`clientKeyFile`・`serverCaFile`・`timeout`（設計概要 §7.1、README の「取得先の登録簿」）。
- 証明書と鍵のファイル名は登録簿からの相対パスで書き、同じディレクトリに置く。

| ファイル | 作る側 | 内容 |
|---|---|---|
| クライアント証明書と鍵 | aka-radius のノード（鍵はノードの外に出さない） | 証明書を aka-vecgen に AV クライアントとして登録する |
| サーバーの CA | aka-vecgen | aka-vecgen の AV 用のサーバー証明書（自己署名）そのもの。これだけを信頼する |

- auth と admin は同じディレクトリを読み取り専用でマウントする。admin は鍵を読まず、ID と証明書の情報だけを読む（`/sources`・`/status`。段階 2-3 の G4）。
- 登録簿を直したら `docker compose kill -s HUP auth admin` で両方に読み直させる。auth は、加入者が指している取得先を消す読み直しを断る。

### 4.2 同じホスト・別のホスト

| 配置 | 登録簿の `baseUrl` | 重ね合わせ |
|---|---|---|
| 同じホスト（MVP のデータ面） | `https://aka-vecgen:8443/nudm-ueau/v1` | `docker-compose.aka-av.yml` を重ねる |
| 別のホスト・ほかの実装 | `https://<相手のアドレス>:<ポート>/nudm-ueau/v1` | 重ねない。相手のサーバー証明書の SAN にそのアドレスが入っていること |

- 平文の HTTP は使えない（mTLS だけ。設計概要 §3.1 の 3）。

### 4.3 運用で気をつけること

| 項目 | 内容 |
|---|---|
| 加入者は 2 か所 | 鍵と SQN は aka-vecgen、状態・取得先・ルールは aka-radius に持つ。どちらも aka-ossbss から aka-provisioner を通して登録する。どちらかで止めれば認証は通らない |
| 遮断器は取得先ごと | 1 つの取得先の障害がほかの取得先の認証を止めない（本PoC は 1 つの遮断器だった）。未登録・無効のクライアント証明書は TLS で断られ、一時的な誤りとして数えられる |
| 確かめ | `sources check` で、形、証明書と鍵の組、期限（30 日より近ければ警告）、各取得先に TLS でつながり HTTP の応答が返るかを見る |
| 証明書の入れ替え | 運用ガイド 7.2。読み直すと取得先のクライアントを作り直す |
| ログの突き合わせ | auth のトレースID を `X-Trace-ID` で送るので、aka-vecgen のログの `trace_id` と突き合わせられる。aka-vecgen のログも同じ Fluent Bit に送る（6.2） |

## 5. Valkey

### 5.1 設定

| 項目 | 値 | 理由 |
|---|---|---|
| 永続化 | AOF（`--appendonly yes`、`--appendfsync everysec`） | 本PoC のまま。1 秒分までの書き込みを失いうる |
| スナップショット | Valkey の既定の `save` のまま | バックアップのスクリプトは `BGSAVE` で取る |
| メモリーの上限 | `--maxmemory 1gb` | 加入者 20 万件で約 100 MB、利用の集計 7 日分で数百 MB の見込み（設計概要 §6.1）。規模の試験で測る。本PoC は 512 MB |
| 上限を超えたとき | `--maxmemory-policy noeviction` | 加入者やセッションを黙って消さない。書けなければ誤りになり、acct は Accounting-Response を返さない（D-10） |
| 認証 | `--requirepass`（`.env` の `VALKEY_PASSWORD`。アプリには `RADIUS_VALKEY_PASSWORD` で渡す） | 空なら compose が設定の読み込みで断る（`${VALKEY_PASSWORD:?…}`） |
| 単一ノード | クラスターにしない | 加入者の Lua の中でキー（取得先ごとの数）を組み立てるため（段階 2-3 の G3） |

- 使うキーと TTL は D-02。

### 5.2 バックアップと戻し

| スクリプト | 作り |
|---|---|
| `scripts/backup-valkey.sh <出力>` | 止めずに `BGSAVE SCHEDULE` でスナップショットを取り、書き終わり（`rdb_saves` が増えたこと）と成功を確かめてから写す |
| `scripts/restore-valkey.sh <スナップショット>` | auth・acct・admin・valkey を止め、AOF を切った一時の Valkey でスナップショットを読み込み、`CONFIG SET appendonly yes` で AOF を作り直してから止める。終わったら `docker compose up -d` |

- AOF が有効な Valkey は、AOF がないとスナップショットを読まずに空で始まる。戻しで AOF を作り直すのはこのため（aka-vecgen と同じ）。
- どちらも動いている valkey がこの compose のプロジェクトに見つからなければ何もしない（プロジェクトを取り違えて別のボリュームを触らないため）。プロジェクト名や重ね合わせを変えたときは `COMPOSE_PROJECT_NAME`・`COMPOSE_FILE` を渡す。
- 写しには RADIUS クライアントの共有シークレットが入る（鍵は入らない）。運用者だけが読める場所に置く。
- 定期の実行（cron など）とバックアップの間隔は、RPO と RTO と一緒に決める（概要 §19）。手順は運用ガイドの 10 章。CI の「README の手順の通し確認」で、取って戻せることを確かめている。

## 6. ログと監査ログ

### 6.1 経路

- auth・acct・admin・valkey のログは、Docker のログドライバー `fluentd`（`fluentd-address: localhost:24224`、`fluentd-async`、バッファー 1 MiB）で Fluent Bit に送る（設計概要 §13。本PoC のまま）。タグは `app.auth`・`app.acct`・`app.admin`・`app.valkey`。
- Fluent Bit は `forward` の入力で受け、`parser`（JSON）で `log` を展開し、タグごとにファイルに書く。
- データ面の aka-vecgen も同じ Fluent Bit に送る（aka-vecgen の `compose.fluent-bit.yaml` を重ねる。タグ `app.vecgen`・`app.vecgen-valkey`。段階 2-5 の K14）。
- `fluentd-async` なので、Fluent Bit が止まっていてもアプリは止まらない（バッファーがあふれた分のログは落ちる）。監査ログはこの経路を通さず、アプリが直接書く（6.4）。
- `docker compose logs` でも見られる。
- Fluent Bit のイメージは distroless なので、シェルに入って調べるときは `-debug` のタグのイメージを使う。

### 6.2 ログのファイル

| ファイル（`logs_on_host/`） | 内容 |
|---|---|
| `auth.log` | 認証、取得先、遮断器、`SIGHUP` |
| `acct.log` | Accounting、利用の集計、セッションの掃除 |
| `admin.log` | 管理API の要求、監査ログを書いたこと（`AUDIT`）、読み直し、監査ログのファイルの圧縮と削除。コマンド（`docker compose exec admin aka-radius …`）のログはその標準出力に出る |
| `valkey.log` | Valkey |
| `vecgen.log`・`vecgen-valkey.log` | aka-vecgen とその Valkey（重ね合わせたとき） |

- 形は JSON の 1 行に 1 つ（D-04）。IMSI はマスクしない（`RADIUS_LOG_MASK_IMSI` の既定 `false`。概要の決定事項 26）。ファイルを読める人をノードの運用者と監視用の PC に限る。
- 本PoC のログは認証 1 回あたり約 2.5 KB だった。ピーク 50 TPS が続く日でも数 GB に収まる見込みで、規模の試験で測る。

### 6.3 ローテーション

- ホストの logrotate で、日ごとに圧縮し、14 世代（2 週間）持つ（設計概要 §13。本PoC は 30 世代）。設定の例は運用ガイドの 9.1（`/etc/logrotate.d/aka-radius`、`daily`・`rotate 14`・`compress`・`delaycompress`・`dateext`）。
- ノードより長い保管は、監視用の PC が取りに行って持つ（概要 §13）。

### 6.4 監査ログのファイル

- admin が `audit/audit-YYYYMMDD.jsonl` に追記する（日付は日本時間）。前の日までのファイルは admin が起動のときと 1 時間ごとに gzip で圧縮し、`RADIUS_AUDIT_RETENTION_DAYS`（既定 14）日を過ぎたら消す。
- Valkey の Stream `audit`（`RADIUS_AUDIT_MAX_LEN`、既定 10000 件）にも書く。項目と `action` は D-13 の 8 章。
- admin は起動のときにディレクトリに書けるかを確かめ、書けなければ起動しない（`AUDIT_DIR_ERR`）。

## 7. 環境変数の要点

compose は `.env` の変数から、アプリが読む `RADIUS_*` を組み立てて渡す。全部の一覧は README の「主要な環境変数」、読み込みは `internal/envconf` と各サブコマンドの `config`。

| 変数（アプリが読む名前） | 既定 | どこで | 要点 |
|---|---|---|---|
| `RADIUS_VALKEY_HOST`・`RADIUS_VALKEY_PORT`・`RADIUS_VALKEY_PASSWORD` | `valkey`・`6379`・必須 | 共通 | パスワードは `.env` の `VALKEY_PASSWORD` から |
| `RADIUS_LOG_LEVEL`・`RADIUS_LOG_MASK_IMSI` | `INFO`・`false` | 共通 | D-04 |
| `RADIUS_HEALTH_ADDR` | `127.0.0.1:9090` | 共通 | 3.6 |
| `RADIUS_AUTH_LISTEN_ADDR`・`RADIUS_ACCT_LISTEN_ADDR`・`RADIUS_ADMIN_LISTEN_ADDR` | `:1812`・`:1813`・`:9444` | 各サブコマンド | コンテナの中の待ち受け。公開先は `RADIUS_UDP_BIND`・`RADIUS_ADMIN_BIND`（compose の変数） |
| `RADIUS_FALLBACK_SECRET` | 空 | auth・acct | 2.3 |
| `RADIUS_REQUEST_TIMEOUT`・`RADIUS_MAX_INFLIGHT` | `4s`（0.5〜30 秒）・`256` | auth・acct | 要求の期限（取得先のタイムアウト 3 秒より長く、エッジの再送の間隔 5 秒より短く）と同時処理の上限 |
| `RADIUS_STAMP_VENDOR_ID`・`RADIUS_STAMP_VENDOR_TYPE` | `32473`・`1` | auth・acct・admin | エッジの設定と同じにする |
| `RADIUS_EAP_AKA_PRIME_NETWORK_NAME` | `WLAN` | auth | EAP-AKA' の `anId` と AT_KDF_INPUT |
| `RADIUS_SOURCES_FILE` | `/etc/aka-radius/sources/sources.json` | auth・admin | 4.1 |
| `RADIUS_ADMIN_TLS_CERT`・`RADIUS_ADMIN_TLS_KEY` | `/certs/server.pem`・`/certs/server.key` | admin | 3.3 |
| `RADIUS_ADMIN_CLIENTS_FILE` | `/run/secrets/admin-clients` | admin | D-13 |
| `RADIUS_ADMIN_NODE_NAME` | ホスト名 | admin | `/status` の `nodeName` |
| `RADIUS_AUDIT_DIR`・`RADIUS_AUDIT_RETENTION_DAYS`・`RADIUS_AUDIT_MAX_LEN` | `/var/lib/aka-radius/audit`・`14`・`10000` | admin・コマンド | 6.4 |

- compose だけが使う変数: `VALKEY_PASSWORD`（必須）、`RADIUS_UDP_BIND`・`RADIUS_ADMIN_BIND`（`127.0.0.1`）、`RADIUS_ADMIN_SHARED_NETWORK`（`aka-radius-admin`）、`AKA_SHARED_NETWORK`（`aka-av`）、`RADIUS_VERSION`（`dev`）、`COMPOSE_FILE`。
- 時刻はコンテナに `TZ=Asia/Tokyo` を渡す。利用の集計の日と監査ログのファイルの日はアプリが日本時間で決めるので、`TZ` によらない。ホストの時刻は NTP で合わせる（Event-Timestamp と受け取った時刻を比べるため）。
- 本PoC の `REDIS_*`・`LOG_LEVEL`・`RADIUS_SECRET`・`VECTOR_*`・`PROVISIONING_*`・`TEST_VECTOR_*` はなくした（段階 2-1〜2-5）。
